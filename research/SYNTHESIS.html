Research synthesis · 2026-08-26

Goblin Foundry Field Notes

What two rounds of research say about building an open-source, pi-based software factory that runs its agents in cloud sandboxes. This is the material a blueprint gets drawn from — the facts, the reusable parts, the tensions, and the questions still open — not the blueprint itself.

00Givens, and what the corpus turned out to be

Fixed before research started: the agent runtime is pi (earendil-works/pi, formerly badlogic/pi-mono — same repo, transferred April 2026), it is a solo project that will be open-sourced, and workers run in cloud sandboxes. Every "fit" judgment below is filtered through those three constraints.

The requested resources sorted themselves into roles cleanly, which is itself a finding: no single source ships isolation + acceptance + queue together. Sandcastle is execution plumbing, Super Simple Software Factory is a control plane, SwarmForge is an inter-agent protocol, fusion-harness is a definition-of-done primitive, Pocock's skills are the human-facing process, and the blogs are the field evidence for why any of it matters. The blueprint will be a composition.

Two lucky facts. Several requested resources are already pi-native: fusion-harness and SSSF run only on pi, exe.dev's image ships pi prebuilt, E2B/Vercel/Daytona/Sprites have first-party pi templates, and SlopCodeBench has a pi.yaml adapter. Choosing pi did not cost compatibility with this corpus — it bought it.

01Eight theses the evidence supports

Cross-cutting conclusions that showed up independently in more than one theme. A blueprint that contradicts one of these should have a reason.

1 · Agent proposes, code disposes.

Sequencing, retries, gates, completion checks and merges are code the factory owns; agents are bounded nodes returning typed envelopes. Every rigorous source (SSSF, bmad-loop, Stripe Blueprints, Uber AutoCover) converges here; the agent-driven variants (Sandcastle's merger agent, Ralph deciding "done") are where the documented failures live.

B §1.2 · D §1.8 · runtime/disler-pi-factories.md

2 · pi is deliberately empty where a factory needs the most — and that is fine.

No permissions, sandbox, subagents, MCP or orchestration in core; ~35 extension events, tool override with operations injection, --mode rpc/json, and appendEntry are enough to build the entire worker side without forking. Orchestration belongs outside pi anyway (thesis 1), and the maintainers explicitly want it there.

A §1.1–1.3, §1.13 · runtime/pi.md

3 · Fresh context per task; resumed session per correction.

Ralph, afk-workflow, GSD, QRSPI and bmad-loop all restart context per ticket/stage; SSSF and Sandcastle show that re-prompting the same session on a gate failure costs one message where a restart throws away everything learned. Never resume across a model change.

B §1.4–1.5, §3

4 · "Done" is a stack of oracles; only deterministic ones may block.

Build → lint → tests → diff-coverage → weak-oracle scan → diff-scoped mutation block; LLM graders rank and filter; held-out checkpointed evals judge the harness, not the PR. 80% of agent-written test patches carry no real oracle — the gate must check that tests can fail.

C §1.1–1.4 · validation/validation-landscape.md

5 · Hold the verifier out of the agent's reach.

StrongDM stores scenarios outside the repo; SWE-bench discards test-file edits; FrontierCode requires agent tests to fail on the pre-patch tree; fusion-harness proves its gate RED before the build starts. In-repo tests serve the inner loop; held-out acceptance is the definition of done.

D §1.9 · C §3 · skills-agents/fusion-harness.md

6 · Every factory with published throughput still has a human merge gate.

Stripe (1,300 minion PRs/week, all human-reviewed), Ramp, WorkOS, Uber. The one lights-off shop publishes no outcomes; HumanLayer's lights-off run ended in a rewrite. The solo answer is "lights-dim": intake assigns a lane (L3 read every diff / L4 read the PR / L5 sampled) and defect rate is logged per lane.

D §1.1, §5 · blogs/dexhorthy-*.md

7 · Per-VM isolation makes worktrees, jj workspaces and file locks moot — but not provenance.

Every worktree orchestrator assumes a shared checkout on one machine, which cloud sandboxes remove. What survives: deterministic branch names, provenance trailers in commits + PR body, a tool-call-granular snapshot journal, stacked PRs, and a merge queue whose failures re-enter the still-live session.

C §1.11–1.16 · git-snapshots/landscape.md

8 · Context is scarce; instruction budget is a hard constraint.

~100-line router file (OpenAI), CLAUDE.md <60 lines (HumanLayer), models silently drop steps past ~150–200 instructions, "a 1,000-line plan contains as many surprises as 1,000 lines of code." Guardrails go into gates and scripts, not prompt text; pi's short prompt and 3× lower context per turn is a real cost advantage.

B §1.12 · D §1.7 · A §1.16

02The layer map

The corpus decomposes into seven layers. For each: what we know, the candidate parts with verdicts, and the tension a blueprint must settle. Verdict legend — adopt use as-is or near-verbatim · adapt port the design, rewrite the code · reference steal ideas only · skip.

L1 · Intake & alignment (the day shift)

Where a human turns intent into work an agent can finish unattended. Every source agrees this is the only ceiling-raising lever a solo dev has; the harness only raises the floor.

Known
Four alignment phases (product review with mockups → architecture → program design as call-stack trees / file-tree diffs → 1–3 vertical slices per session) cut rework from 20–50% on one-shot PRs; ~40% of tasks are one-shot and skip it. Pocock's chain (grill-with-docs → CONTEXT.md + ADRs → to-spec → to-tickets → triage) is the packaged version and its skills load unchanged in pi. Wayfinder adds a map (destination / decisions so far / not yet specified / out of scope) and typed decision tickets, with HITL vs AFK tagging.
Parts
adopt mattpocock/skills day-shift chain as-is · adopt Wayfinder map + ticket types · adapt QRSPI-lite (Q → ticket-hidden research → ~200-line design doc deep-reviewed → structure "header file" → spot-checked plan) · adapt Spec-Kit's three templates (spec/plan/tasks.md, [P] markers) · adopt SSSF operator skill ("print the menu and wait", four-line prompt: ask / where / done-means / out-of-scope) · skip BMAD personas, GSD command router.
Tension
Skills vs owned process. Pocock: small composable skills, "fix the failure modes, don't own the process"; GSD/BMAD/Spec-Kit own the phase sequence. Middle seen in SSSF and Spec-Kit's converge: phases in code, phase content as skill files. pi caveat: model-invoked skills are less reliable than in Claude Code, so AFK phases must force-load (--skill, before_agent_start).

L2 · Control plane (queue, scheduler, phases, gates)

The deterministic program that owns the task graph and calls agents as nodes. Lives outside the sandbox, stateless across restarts, treats the tracker as truth.

Known
Planner emits a dependency graph; scheduler runs the ready frontier (open ∧ unblocked ∧ unclaimed) — same shape in Sandcastle, fusion-harness, implement-spec, GSD waves, Spec-Kit, Symphony. Markdown plan files do not survive >1 worker; Beads gives atomic bd ready --claim --json, hash IDs, blocks edges, gates (human | timer | gh:run | gh:pr) and execution metadata (suggested model, effort, parallel group). Symphony's SPEC (Unclaimed → Claimed → Running → RetryQueued → Released, max_turns 20, 5-min stall, exponential backoff capped at 300 s, nothing persisted across restart) is the most complete public state machine. Triage is a state machine with transitions agents may not make (needs-triage, wontfix).
Parts
adopt SSSF phase primitive + typed envelope triad (schema ↔ prompt example ↔ call site) + post-hoc gates (artifacts_exist, diff_matches_claims, verdict_consistent, tests_pass) + permission-by-diff with protected_files — rewritten in TS over pi · adopt Beads on the controller as the queue (one issue per VM via prompt; server mode deferred) · adopt Symphony/AO state machine + Stripe's two-CI-round cap · adopt role = tool allowlist (READONLY/FULL/VALIDATOR) + writer lease · adopt Sandcastle produce-then-extract, two-phase timeouts, {{ARG}} substitution as injection boundary, deterministic branch names · adapt bmad-loop's orchestrator design (policy.toml budgets, hook-event files, separate dev/review sessions, CRITICAL/PREFERENCE escalation, deferred-work ledger) · adapt humanlayer design-control-loop for every recurring lane, bounded to one open PR · reference SwarmForge inbox/outbox handoff + two-call audit gate (no license — reimplement semantics only) · skip in-session Stop-hook ralph plugin (doesn't reset context).
Tension
Beads vs GitHub Issues vs markdown as the tracker. Beads is the only correct multi-worker queue but is Dolt/Go weight that must be pinned into images; GitHub renders the frontier natively ("blocking is what renders the frontier visually") but needs gh and API rate in the loop. Leading option: Beads as queue on the controller, GitHub as human UI via bd github sync.

L3 · Worker runtime (pi inside the sandbox)

One pi session per task, driven headlessly. Everything factory-specific is a TypeScript extension pre-baked into the image.

Known
Three headless seams in maturity order: pi --mode rpc / --mode json -p JSONL on stdio (stable, any controller language, extension_ui_request gives headless HITL); SDK createAgentSession() in-process (stable, TS-only); pi-server/client/protocol (leases, authoritative snapshots — "may be removed without notice", no shipped service). --session-id is create-or-continue, so "run" and "re-prompt with a correction" are the same call. Gotchas: close stdin when spawning pi -p; split RPC frames on \n only. Session JSONL is the audit artifact everywhere and is mid-migration (v3 tree → v4 durable records + SQLite) — pin pi version, treat layout as versioned data. Opus 4.8/Sonnet 5 invent tool fields on pi's stricter edit schema because they were RL-trained in Claude Code's forgiving harness. Databricks (Aug 2026): pi + Opus 4.8 highest pass rate, ~3× less context per turn, >2× cheaper per task than Claude Code/Codex.
Parts
adopt --mode rpc per task · adopt tool_call policy hook (block/mutate/terminate) + tool_result scrub/truncate · adopt terminate:true structured output for envelopes · adopt appendEntry for task id / checkpoint SHAs / gate verdicts · adopt provider hooks for telemetry, budget kill-switch, gateway routing · adopt Agent Skills spec frontmatter as the portability line (identical in pi and Claude Code; disable-model-invocation honored by both) · adapt official examples (git-checkpoint.ts, subagent/, ssh.ts, sandbox/) by vendoring · adapt Claude-hook-JSON shim in one extension so existing hook scripts run unchanged · adapt clean-room children (--no-skills --no-extensions --no-context-files) with explicit --skill · reference 30+ subagent packages (capability ceilings, launch-contract digests, gate:"npm test", journaled resumeFromRunId) — never install in workers · reference pi-server lease/snapshot semantics for the controller's own protocol.
Tension
Agent-in-VM (works today, every provider demos it, VM must hold some LLM credential unless proxied) vs tools-in-VM via Gondolin/ssh.ts (credentials and sessions central; needs nested virt on the controller host; controller crash kills every in-flight session). Read: A now, but write the worker extension so it also works under B. Sub-agents inside a worker vs fan-out in the controller: maintainers call sub-agents "a black box within a black box"; workers stay single-session, fan-out lives in the controller.

L4 · Sandbox / execution substrate

The cloud VM each worker runs in. Isolation is the only security boundary because pi runs YOLO inside it.

Known
The landscape has converged (microVM, TS SDK, sub-2 s start, SNI egress allowlists). Differentiators: plan floor vs per-second billing; fork-1:N from a warm state (E2B, Vercel, boxd, Morph yes; Sprites, Cloudflare, exe.dev no — it is the cloud replacement for git worktrees); secrets injected at the edge so the VM never holds a key (Vercel, Cloudflare, Daytona, exe.dev, Gondolin). Firecracker cannot bind-mount a checkout — every cloud path needs a sync strategy (push refs/sandbox/<run> vs pull diff/bundle). Reference workload 10 × 2 vCPU × 4 h/day ≈ 880 sandbox-h/mo costs $30 (Sprites) → $350 (E2B); the unmeasured variable is real CPU duty cycle while waiting on the LLM. Ramp/Stripe/Uber all rebuild a warm image on a cron (<10 s start) — latency is the adoption lever. Daytona went closed-source in June; Cloudflare 1.0 preview breaks the API; treat every provider as replaceable behind a small interface.
Parts
adopt E2B as primary candidate (pause-with-memory, fork({count}), official pi template, Apache-2 infra; $150 floor, idle billed) · adopt Vercel Sandbox as second implementation (pi preinstalled, fork, best credential brokering, active-CPU billing; 24 h cap) · adapt exe.dev / Sprites for a small persistent-bot tier (merge-queue repair, flaky-test fixer) · adopt Inkwell credential boundary (host holds provisioning key; VM gets capped, revocable sbx- runtime key) as provider-agnostic fallback · adopt own Docker image with ARG PI_VERSION · reference Gondolin (best OSS secrets story; needs nested virt) and OpenShell (YAML policy, K8s gateway) · reference Amp orbs (setup-then-snapshot, services.yaml portals, per-thread OIDC) as a repo-side contract · skip Modal for now.
Tension
Ephemeral fork-per-task (E2B/Vercel) vs long-lived restored pool (Sprites/exe.dev): drives provider choice and depends on the duty-cycle measurement nobody has done. Secrets: proxy injection (never in VM, TLS interception, lock-in) vs capped runtime key (provider-agnostic, disposable) vs plain env — layer them. Egress allowlists are SNI/Host-only everywhere → git over HTTPS only.

L5 · Validation (oracles, gates, evals)

What decides "done" — for a tool call, a phase, a PR, and the harness itself. Ordered by cost and by how hard each oracle is to fool.

Known
Three independent production/practitioner orderings agree: build → lint/typecheck → tests → diff-coverage (≥80% on changed lines) → weak-oracle scan → arch/dup rules → diff-scoped mutation; LLM review after, as a generate → different-vendor grade → dedupe → suppress chain (Uber: 75% useful, 65% addressed only once chained). Two 5-second "tests can fail" proxies exist besides mutation: the no-op stub check and B/S/G replay on the pre-fix commit (+7.4 pp when fed back). Uncle Bob's per-file zero-survivor rule beats a global percentage (percentages are gamed by adding easy code) — but all his repos are unlicensed. fusion-harness's gate-first pattern (validator writes an executable gate before the build, proven RED at baseline, builder iterates on verbatim FAIL: lines, one gate repair per run) is the strongest definition-of-done primitive found. Evidence gates (deny edit before read; deny commit without fresh verify hash; deny tests/** writes in fix tasks) are ~100-line tool_call hooks and cut tokens 12%. SlopCodeBench (checkpointed specs, hidden black-box tests, cumulative regression, canaries) is the only oracle for the harness itself and already drives pi; no model solves any problem end-to-end (best 24–33% strict).
Parts
adopt tiered make verify (fast / verify / deep) emitting verify.json · adopt diff-coverage, weak-oracle AST scan, no-op stub check, B/S/G replay · adopt incremental diff-scoped mutation (Stryker --incremental, mutmut --CI, gremlins) pre-merge + full nightly · adopt zero-survivor-per-file rule on new functions (rule, not binary) · adapt fusion-harness gate-first acceptance · adapt uReview chain as a second pi session with one global threshold + 30–50 PR golden set · adopt ECLoop-style evidence gates as pi extensions · adopt held-out cumulative acceptance (SCBench marker scheme) as definition of done for multi-slice epics; weekly SCBench run on 3–5 private problems as harness CI · adapt APS acceptance-data mutation (~500 lines to reimplement) nightly · reference LLM judge rubrics (report, never gate), property-based sweeps, Uber AutoCover's bounded "do no harm" fixer.
Tension
Held-out evals vs in-repo tests: hidden tests are the only oracle "fooled by nothing cheap" but the worker cannot run them in its inner loop. Resolution: both — in-repo for the loop under a tests/** write policy; held-out in the orchestrator as done. Grader vendor diversity (Uber's best F1 used a second vendor) vs one-account simplicity. Mutation cost vs signal: incremental + proxies in the loop, full nightly.

L6 · Versioning, provenance & integration

How agent work becomes commits, PRs and merges — and how every line stays traceable to the session that wrote it.

Known
Both "agent-native VCS" products are vendor traps today: Zed Delta/DeltaDB (operation-level CRDT deltas adjacent to messages) is a closed private beta with no API; Cursor Origin's agent features (provenance, agent principals, machine-readable review state, agent-aware merge queue) are announced, not shipped. Both confirm the direction and every piece is emulable on git + pi session + trailers. jj inside a VM gives tool-call-granular undo (jj util snapshot on tool_result, jj op restore) with no custom format, but has no hooks, change IDs die in GitHub squash, and agentjj's post-mortem shows absorb/squash/colocated-git confuse agents. GitHub merge queue is GA and free (merge_group CI, gh pr merge --auto, dequeued event → repair); gh stack is preview with no API; git-spice is the scriptable OSS stacker; Graphite is now Cursor-owned. exe.dev: "by the time automated failures arrive, the agent context window is dead and gone" — the merge queue is the CI, and its failures must land while the session is alive.
Parts
adopt v1 git write-tree journal → refs/factory/<session>/<n> + JSONL {session, turn, tool_call_id, tree} · adopt provenance trailers (Agent-Session / Agent-Model / Agent-Task / Agent-Prompt-Sha / Agent-Runner) from pi's PI_SESSION_ID/PI_MODEL env, copied into the squash message via PR template + CI presence check · adopt message↔edit adjacency as a pi session custom entry · adopt agent/<task-id> branch from fresh base, task metadata in PR body, TTL sweeper · adopt git-spice stacks + GitHub merge queue with dequeue → resume-same-session repair, cap 3 → "Needs You" · adopt one GitHub App identity per agent role so the bot can never self-approve · adapt jj in-VM snapshots as a v2 experiment with a tiny agent verb set · reference ACP's tool_call{kind,status,locations,content:[diff]} as the neutral event-log shape (pi is not ACP-native; --mode rpc is richer) · skip worktree orchestrators (Vibe Kanban sunsetting, Conductor closed) except AO's state machine · skip Mergify/Depot until >~20 PRs/hour.
Tension
Squash (simplest queue; kills per-commit trailers and jj IDs → trailers via PR body) vs rebase (keeps trailers and agent noise). jj vs plain git: 80% of the value from write-tree with zero new dependency. Freeze trailer names now vs wait for Origin/ACP to publish a de-facto standard: freeze, rename via CI mapping later.

L7 · Observability, routing & the outcome dataset

Traces for kill-ability and replay, a model-routing document, and the per-PR outcome telemetry nobody in the corpus publishes.

Known
SSSF's single SQLite WAL trace (7 tables, one rowid > ? cursor, a processes table for kill) is the cheapest observability that handles "goes quiet rather than red." pi's session JSONL + provider hooks are the exporter seam; pi-telemetry and pi-evals are experimental but shaped right. StrongDM's Weather Report (model × role × reasoning-effort, updated monthly) and Devin Fusion (frontier decider + cheap executor, switch at compaction: within 2 points of Fable 5 at 1/8 cost) make "one model for everything" obsolete. Faros: while merges rose, incidents/PR +243%, churn 10×, review time 5×, deploys −12% — "throughput measures what was shipped, not what survived."
Parts
adopt SSSF trace schema (with processes) · adopt WEATHER.md routing table; Beads execution metadata feeds it · adopt per-run + per-PR JSONL outcome rows (see §05) · adapt pi-web as the interim fleet dashboard · adapt OpenAI/Uber scheduled GC loops against docs/golden-principles.md, capped at 3 open PRs · adapt weekly manual skill distillation from session logs · reference pi-telemetry → OTel when stable.

04Decisions the blueprint must make

The places where the sources genuinely disagree, or where two viable options exist. Each shows the options, the evidence, and where the corpus leans — the lean is an input to the blueprint, not a verdict.

D1 · Ephemeral fork-per-task or long-lived worker pool?

Fork per task E2B / Vercel. Warm clone in seconds, clean state, idle billed, plan floor $150 (E2B).
Restored pool Sprites / exe.dev. $20–50/mo realistic, pooled CPU caps true parallelism, no fork, state reset by restore.

Lean: fork-per-task for build workers, a tiny persistent tier for bots — but the choice hinges on measured CPU duty cycle (Q-A2), which nobody has published.

D2 · Agent-in-VM or tools-in-VM?

Agent in VM One pi --mode rpc per sandbox; any controller language; session stays with workspace; VM holds an LLM credential unless the provider proxies it.
Tools in VM pi on the controller, read/write/bash relocated via Gondolin/ssh; secrets central; needs nested virt; controller crash kills every session.

Lean: agent-in-VM now, with the provider-side secret proxy removing its main weakness; write the worker extension against the same API so B stays possible.

D3 · Who writes the acceptance gate, and in what language?

Validator agent per ticket fusion-harness: separate model writes gate.py before the build, proven RED. One extra frontier call + baseline run.
Human criteria + tests only to-tickets acceptance criteria compiled by a cheap model; tests_pass + held-out suite for v1.

Lean: define a language-neutral gate.sh contract (exit 0 iff done; PASS:/FAIL: lines) and start with human-authored criteria; add the validator agent when ticket quality supports it.

D4 · Tracker of record: Beads, GitHub Issues, or both?

Beads on the controller Atomic claim, blocking edges, gates, execution metadata; Dolt/Go weight, single-writer embedded mode.
GitHub Issues + labels Native frontier rendering, human UI, Sandcastle's label state machine; needs gh and API rate in loop.

Lean: Beads as queue, GitHub as human UI via bd github sync, one issue per VM passed by prompt. Needs a --claim concurrency test first (Q-B1).

D5 · Session policy per stage

Fresh every stage bmad-loop: review never inherits the implementer's context; no anchoring.
Resume within a stage SSSF: a correction costs one message; bounded by max_dev_attempts.

Lean: fresh per ticket and per stage; resume only for gate corrections within a stage; never across a model change. Write the matrix (plan / build / fix / review / extract / merge × fresh-or-resume × cap × model) explicitly.

D6 · Results sync: workers push, or controller pulls?

Push Worker pushes agent/<task> or refs/sandbox/<run>; needs a push credential in the VM (brokered or capped).
Pull Controller pulls git diff/bundle; VM holds nothing; controller does all history work.

Lean: push to a namespaced ref with a per-run GitHub App token; the orchestrator owns stacking, squash and merge (C §5). Prototype both on the chosen provider.

D7 · Lights-off lane criteria

Three lanes at intake L3 read every diff · L4 spec + scenarios, read the PR · L5 sampled review only.
Uniform human gate Every PR read; simplest; review becomes the bottleneck immediately (Faros).

Lean: three lanes; L5 initially only for {dep bump, GC refactor, lint fix} with diff <100 lines, in-scope files, all held-out scenarios green, no slop-metric regression; 30-day defect check per lane before widening.

D8 · Merge strategy and provenance

Squash Simplest for the queue; per-commit trailers and jj IDs die → carry trailers in the PR body.
Rebase Trailers survive per commit; agent noise commits survive too.

Lean: squash + PR-body template with a CI presence check; tool-call granularity lives in the journal and session, not git history.

D9 · Review grader: one vendor or two?

Two vendors Uber's best F1 (Sonnet generator + o4-mini grader); graders drift on model updates.
One vendor Haiku-class grader; shares blind spots with the author model; one account.

Lean: undecidable without a 30–50 PR golden set; build the set first, then measure the F1 gap (Q-C9).

D10 · Vendor or rewrite Sandcastle's plumbing?

06What to measure

Nobody in the corpus publishes the outcome dataset Dex Horthy asks for (what survived, not what shipped). A solo factory can — one JSONL row per run and per merged PR, a weekly script as the dashboard.

Per run (pi session)

  • issue id · lane (L3/L4/L5) · model + effort from WEATHER.md
  • tokens in/out · cache hit rate · $ cost · turns used vs max_turns · wall time
  • terminal state (Symphony: done / stalled / timeout / released) · CI rounds used (cap 2)
  • inner-loop checks passed (validation table) · diff size · files touched vs declared scope

Per PR (outcome)

  • human read it? (yes / sampled / no) · review minutes · rework % after first review
  • review-agent comments posted / addressed (re-run reviewer on final commit)
  • time to merge · reverted? · 14-day churn · incidents linked within 30 days

Repo trajectory (per merge)

  • SLOC · cyclomatic mean/max · duplication share · single-use-function share · files >350 lines · dependency cycles
  • alarm on inflection, not level (SlopCodeBench checkpoint-3 pattern)

Platform & harness

  • sandbox cold-start s (target <10) · snapshot age · $/day (budget $20–50) · $/merged PR · $/surviving PR
  • review-agent precision on a 30–50 PR golden set; re-pick model pair when F1 moves
  • weekly SlopCodeBench-style run on 3–5 private checkpointed problems: strict-pass + erosion inflection
  • PRs/week and deploys/week side by side — divergence is the Faros "hollow gain" signal. Never "% code by AI."
