## One-paragraph summary

Part 1 claimed "THERE ARE NO GOOD BENCHMARKS for a model's ability to maintain codebase quality"; part 3 walks that back to introduce **SlopCodeBench** (Gabe Orlanski's lab, UW Madison, March 2026), a long-horizon benchmark where each challenge is divulged as a series of *checkpoints* so the model must evolve a codebase against requirements it hasn't seen yet. Dex ran Opus 4.8, Sonnet 5 and Opus 5 in the Claude Code harness on 3 problems / 17 checkpoints (fresh context per checkpoint, "just-solve" prompt, no quality guardrails), watched for six hours, and reports Opus 5 at 4/17 strict passes (24%) vs 1/17 (6%) for the others; nobody reached the end of any challenge defect-free. Deterministic "slop meter" metrics (41 of them) show complexity, verbosity and (for older models) duplication rising across checkpoints. His conclusion: SlopCodeBench is "something you can measure" that backs the vibes from part 1 — "today's models can't be relied on to run lights-off without steering" — and he'd only trust lights-off at "80%+ on a (well-held-out) benchmark like SlopCodeBench."

## Core ideas / thesis

- **Incrementally-divulged specs are the right oracle for maintainability.** "'pass all verifiers for an incrementally-divulged spec' is a very realistic eval for 'can a model maintain a codebase over time'... a codebase becoming hard to maintain would lead to failing checkpoints in later stages."
- **Deterministic black-box verifiers beat model-as-judge.** Slow (8 checkpoints vs a 15-min SWE-bench task) but "it can be executed unattended and is subject deterministic behavior verifiers at the end. So IMO its a much better oracle than e.g. 'does another model think this code is clean'."
- **Complexity grows over time for all models — now with data.** "I've been saying models degrade codebase quality over time for about a year now, mostly on vibes. But now we have some data. Not a single model made it through all the challenges without increasing complexity across checkpoints."
- **Slop metrics are directional, not golden.** "I'm not totally sold on 'linting the slop away'... the link between any one of them and 'is this codebase easy to change and evolve' is not yet established." Also "easy for a model to reward hack any of them."
- **Proposed amplifier: smart model builds, dumb model extends.** "have a frontier model like opus 5, fable 5, or gpt-5.6-sol write the first N checkpoints, and see if a dumber model like sonnet 5 or gpt-5.6-terra can implement checkpoint N+1... Whether a small model like Sonnet or Terra or even Haiku can implement checkpoint 8 impacts the smart models' score on checkpoints 1-7."
- **Threshold for going lights-off:** "if/when models can score 80%+ on a (well-held-out) benchmark like SlopCodeBench which measures iteration over time, I'll feel a LOT better about setting them loose with the lights off."

## Architecture & mechanics

**Benchmark structure (SlopCodeBench):** each challenge = ordered checkpoints; "Each one arrives cold — the model has no idea any of the later ones exist." Verification = held-out black-box tests against the produced entrypoint (a CLI, or an API server to poke). Loop:
- Model writes code for ck1 -> harness runs black-box tests for ck1
- Model writes code for ck2 -> harness runs tests for ck1 **and** ck2
- ... (regressions inherited from earlier checkpoints carry forward)

**Strict pass** = "everything new is green including every regression test that was inherited from previous checkpoints." A defect at ck4 sinks all later checkpoints unless accidentally fixed ("we didn't see this happen in practice").

**Dex's run:** Claude selected 3 problems (17 checkpoints): `circuit_eval` (easy, 8 ck — a `.circ` circuit CLI growing vectors, X-logic, extra formats, lint/stats/dot, cone/truth-table/equiv, optimizer), `database_migration` (medium, 5 ck — JSON migration specs on SQLite growing data migrations, FKs/indexes, rollback, depends_on + cycle detection), `dynamic_config_service_api` (hard, 4 ck — versioned config REST service growing schema registry, draft/proposal/quorum workflow, policy guardrails). All three models ran in parallel, **fresh context window per checkpoint**, same "just-solve" prompt, Claude Code harness. Full checkpoint listing is in the article's appendix.

**Results:** Opus 5: 4 strict passes (first 3 ck of circuit_eval + database_migration ck1) = 24%. Opus 4.8 and Sonnet 5: 1 each (6%), the same database_migration ck1. Paper baselines: GPT-5.4 11%, Opus 4.6 17%. Cost note: "every dollar bought correctness. nobody bought enough of it." Sonnet's first checkpoint was most expensive but it became cheapest once work turned to maintenance. Follow-up run (repo): Fable and Sol tied at 33.3% (10/30), Kimi K3 26.7%/23.3%.

**Slop meter (41 deterministic metrics per checkpoint):** size (SLOC, files, functions, classes, statements, lines added/removed); complexity (cyclomatic mean/max/spread, high/extreme bands, concentration, nesting depth, function length); duplication (cloned lines, share); decomposition (single-use functions, trivial wrappers, unused variables, lines per symbol); rule violations (lint errors, auto-fixable count, ast-grep test-slop hits, verbose-line share); dependency graph (propagation cost, cyclic dependency mass, dependency entropy — "probably the most interesting one to me").

**Findings:** 89-98% of lines tripped at least one slop rule (Opus 4.8 98%, Opus 5 93%, Sonnet 5 89%); verbose-line share rose ~65% -> ~80% ck1->ck8 for every model. Opus 5 wrote ~5x more functions (~2000) with lowest mean complexity; Sonnet 5 had 71.5% single-use functions. Opus 4.8 and Sonnet grew individual functions (Opus 4.8 mean complexity +70%, worst function CC=93). Duplication: Opus 4.8 4.6% -> 16.8% with an inflection at ck3 "roughly where new requirements start fighting the initial design"; Opus 5 basically flat 2.41 -> 2.64. Opus 5 wrote ~1.8x the production code of 4.8. A 76-rule TypeScript port (drafted by Sol) found Opus 5 lights-off solutions had ">11 times more slop triggers per kLOC than our 99%-AI-generated-but-also-carefully-reviewed Typescript monorepo" (with "a mountain of asterisks").

## Notable techniques worth stealing

- **Checkpointed, held-out, black-box evals** as the factory's model/harness regression suite — the closest thing to a maintainability oracle that runs unattended.
- **Fresh context per checkpoint** (matches ralph-loop / RPI context hygiene).
- **Metric trajectories, not snapshots:** log duplication, cyclomatic complexity, propagation cost, dependency entropy per PR/checkpoint and alarm on inflection (ck3-style "requirements start fighting the initial design").
- **Small-model-extends-big-model test:** cheap proxy for "is this codebase easy to change" — have Haiku/Sonnet implement the next slice on a codebase Opus built; failure = maintainability smell.
- **Quality backpressure experiments he wants run:** re-run with 1) an adversarial-review loop with a judge model, 2) deterministic code-quality backpressure (cyclomatic complexity etc.) in the loop — i.e., exactly what a factory harness would add. Untested in this post.
- **Parallelize by (model x challenge)**, not by model: "3 models x 3 challenges in 9 parallel sessions... 1-2 hours instead of 6."
- **Port slop detectors to TypeScript** (current SCB detectors are Python-only; 200+ rules).

## Weaknesses / open questions / risks

- Tiny sample: 3 problems, 1 run each; Dex says the subset "cannot tell us definitively."
- "Just-solve" prompt, no CLAUDE.md/quality instructions/hooks — so it measures raw model behaviour, not a well-engineered harness. Results with guardrails are an open question (he acknowledges).
- Slop metrics may be "over-aggressive" (he says so); detectors Python-only; the TS comparison is apples-to-oranges.
- Reward-hackable metrics; contamination risk ("Assuming nobody 'accidentally' trains on test").
- Anecdote at the end ("the frontier is still dumb af": Opus 5 rewrote and sent an email to 100 people unprompted) underlines the agency/safety risk of lights-off operation beyond code.

## Fit for our agentic stack

- **Adopt:** a SlopCodeBench-style internal eval: curate 2-4 checkpointed problems shaped like our real work; run on every harness/prompt/model change; strict-pass + metric trajectories as the scorecard. Use `SprocketLab/slop-code-bench` as the runner.
- **Adopt:** per-PR deterministic quality metrics (complexity, duplication, propagation cost) as CI backpressure — Dex's "raise the floor" — while accepting they don't prove maintainability.
- **Adapt:** the "dumb model extends smart model's code" check as an optional post-implementation probe on high-value modules.
- **Policy:** treat lights-off as gated on an external maintainability threshold (Dex's 80% SCB), not on vibes or SWE-bench-style scores.
- **Skip:** trusting model-as-judge as the sole quality gate.
