## One-paragraph summary

The prescriptive half of the series. Since (per part 1) models can't be trusted as the judge of code quality, "the judge is you -- so we're gonna put the code review back," and the way to keep review cheap is to front-load alignment with AI assistance across four phases: **Product Requirements -> System Architecture -> Program Design -> Vertical Slices**. The under-appreciated step is *program design* (types, signatures, call-stack trees, file-tree diffs, argued with the model before any code), and the under-appreciated execution style is *vertical slices / tracer bullets* (start in the middle, touch the running thing at every step, review 100-200 lines at a time) instead of the "horizontal plans" models default to (migrations -> services -> API -> frontend). Closing stance: "embrace the constraints and move 2-3x faster, safely" rather than chasing 10-100x, and "Read the dang code."

## Core ideas / thesis

- **Put code review back; make it cheap via planning.** "We're gonna embrace that same thing we've been doing since before AI, which is to do a little bit of planning up front, to reduce the odds of a long and difficult review."
- **Four alignment phases** where "humans need to be in the loop for, if you want to maintain a near-human level of quality": Product Design, System Architecture, Program Design, Vertical Slices.
- **Planning artifacts are decisions pulled forward.** "every one of them is a decision you'd otherwise be making implicitly during code review -- at the most expensive possible time to change your mind."
- **"30 minutes of planning saves hours of review."**
- **"You don't have too many PRs. You have too many bad PRs."** A PR needing "even 20% rework (and that's generous, I'd say most AI oneshot PRs trend closer to 50%)" is an intellectual and emotional burden on both sides.
- **Theory of constraints (2026 edition):** "Models are good at some things, not so good at others. How do you optimize your process in light of those constraints?" Closing advice: "1. Learn the constraints well... 2. Optimize systems within the arena of these constraints 3. Seek leverage 4. Read the dang code."
- **Not everything gets the full process** — ~40% oneshot; medium tasks get one combined product/system plan doc; large things get all steps (skip product for big refactors).

## Architecture & mechanics

### Phase 1: Product review
"a short doc that pins down what we're building and why. The goal is to be able to take two sentences or a long voice note ramble and turn it into something semi-structured."
- Align on **the problem** "in the user's terms", then **what success looks like** ("can do XYZ workflow in less time", an error rate, or "the support tickets about X stop").
- Stay in product space; jot technical thoughts for later phases. If tech blocks product, "commit what we have and get into the architecture or do more prototype research."
- **Mock it up, don't describe it:** "A rough HTML mockup of the actual screen settles an argument that three paragraphs would only prolong." Real example: doc = JSON outline of the feature + two rough HTML mockups (https://x.com/dexhorthy/status/2078592010852982977).
- Skip for copy tweaks, one-off scripts, obvious-repro bugs: "This is for the changes where an agent misunderstanding our intent is expensive."
- **Author-opt-in reviews:** "you pick the person who would review the PR, and run through the product/tech specs with them" async via doc comments (HumanLayer dogfoods its own tool; "github/notion/plannotator/etc" work too).

### Phase 2: System architecture
"align on how the services, endpoints, schemas, queues, and stores talk to each other, without getting into the details of program design." Heavy use of visualizations: sequence diagrams, contract/endpoint shapes, data models and transformations. Caveat: "Mermaid is fine here but it can sometimes be overkill and sometimes lure you into a false sense that you are aligned." Architecture "is insufficient to produce high-quality code. For that we need program design."

### Phase 3: Program design ("criminally underemphasized in agentic coding")
"before anyone (human or agent) writes the implementation, we go a level down from architecture into the shape of code: the types, the method signatures, the program layout, and the call stacks." First version of their program-design skill "sucked... exhausting"; mermaid was tried. What works: **light visualizations in pseudocode**:
- **Call-stack trees** for any orchestration/control-flow change, "Use diff syntax when the interesting part is what's changing" (credits Dillon Mulroy's call-graph planning).
- **File-tree diffs** "so you can stay in touch with the layout of your codebase and where stuff lives."
- **Types and method signatures** for key new functions — "too internal for an architecture doc but that an agent might still get wrong."
"None of these take long to produce (the model drafts them, you argue with it)."

### Phase 4: Vertical slices (tracer bullets; cf. Shape Up "integrate one slice")
Models default to **horizontal plans**: 1. Database migrations 2. Service layer 3. API 4. Frontend — "there's no real way to 'touch' the solution as you're going." Dex's pre-AI habit, "start in the middle and work outwards":
1. Create API contract and serve mock data, test with curl
2. Create frontend to consume mock data, iterate+polish in browser
3. Wire API to services layer (services serves mock data/behavior)
4. Add database migrations, wire services to database
5. Add a bunch of business logic
6. Add a bunch of error handling
"testing/iterating/polishing at each step." "Checking 100-200 lines and resteering is a lot cheaper." "Most frontier models won't design a plan like this without human steering... so I prefer to stay in the loop here." Execution: "I'll send off a model to do 1-3 slices at a time, and review the code as I go."

## Workflow: end to end

1. Intake: two sentences or a voice ramble -> **product review doc** (problem, success criteria, HTML mockups). Skip for trivial tasks.
2. Author-opt-in review of the doc by the eventual PR reviewer (async comments).
3. **System architecture doc**: sequence diagrams, endpoint contracts, data models.
4. **Program design doc**: call-stack trees (diff syntax), file-tree diffs, types/signatures. Model drafts; human argues.
5. Plan decomposed into **vertical slices**; agent implements 1-3 slices at a time.
6. Human reviews each slice (100-200 LOC), re-steers early.
7. PR — should be "a joy to review" because it follows the already-agreed decisions.
Distribution: ~40% oneshot / medium = single plan doc / large = all steps.

## Notable techniques worth stealing

- **Two-question product doc**: problem in user terms + observable success metric; everything else deferred.
- **HTML mockups as spec** — generate throwaway HTML screens instead of prose UI descriptions.
- **Author-opt-in spec review by the future PR reviewer** — moves review effort to the cheap end.
- **Program-design artifacts in pseudocode, not mermaid**: call-stack trees with `+`/`-` diff syntax, file-tree diffs, signature lists. These are cheap to generate as a Claude Code skill/command output and cheap to review.
- **Force vertical-slice plans** — an explicit instruction/skill that rewrites horizontal plans into mock-first tracer-bullet slices with a "how do I touch it" (curl/browser) check per slice.
- **Slice-batched implementation**: 1-3 slices per agent session, review in between; never "the other side of 2k+ lines of code."
- **Task triage tiers** (oneshot / single-plan-doc / full four-phase) as an explicit routing decision at intake.
- **Target 2-3x, not 10-100x.** Use this as the factory's stated throughput goal.

## Weaknesses / open questions / risks

- Heavily human-in-the-loop; throughput is bounded by one reviewer's attention. Doesn't say how to scale review across a team or how to decide reviewer allocation.
- The phase docs' formats are described but no templates/prompts are given in the article (HumanLayer's product presumably carries them; older versions exist as `.claude/commands/research_codebase.md`, `create_plan.md`, `implement_plan.md` in the deprecated humanlayer/humanlayer repo).
- The 40/medium/large distribution and "20-50% rework" figures are anecdotal.
- Ends in a product pitch (humanlayer.com IDE); techniques and product are intertwined.
- Some rendering garble around the vertical-slices section in the X article ("If I couldoutsource the thinking" — a mangled link to Jake Nations' "the hard work of thinking can't be outsourced to AI, only amplified by it").

## Fit for our agentic stack

- **Adopt directly** as the factory's *upstream* pipeline: `product-review` -> `architecture` -> `program-design` -> `slice-plan` as Claude Code slash commands/skills, each emitting a markdown artifact into a `thoughts/` or `docs/plans/` directory that the next stage consumes. Human gate after phases 1, 3 and each slice.
- **Program-design skill:** have Claude produce call-stack trees (diff syntax), file-tree diffs and type signatures; reject plans that lack them for orchestration/control-flow changes.
- **Slice planner:** post-process any plan: if phases are ordered DB->service->API->UI, rewrite to mock-API-first vertical slices with a per-slice "touch test" (curl/browser/CLI).
- **Intake router:** classify tasks into oneshot / plan-doc / full-process; only the last two enter the multi-phase pipeline.
- **Review economics dashboard:** track rework % per PR; goal is PRs "a joy to review."
- **Skip/adapt:** the HumanLayer product itself is optional; GitHub PR comments / plain markdown files serve the same author-opt-in review role.
