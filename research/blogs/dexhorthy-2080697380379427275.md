## One-paragraph summary

Dex's counter-argument to the "lights-off software factory" narrative (StrongDM, OpenAI Symphony/harness engineering, Ramp, Stripe, WorkOS, Brex). His claim: no amount of harness engineering, loop-writing, or "tokenmaxxing" fixes the fact that current models degrade codebase maintainability over time, because that failure is a *model-training* problem. Coding RL rewards pass/fail test outcomes in seconds (SWE-bench style FAIL_TO_PASS / PASS_TO_PASS), while the cost of bad architecture only shows up weeks-to-years later, so there is no fast oracle to reward good design. HumanLayer tried going fully lights-off in July 2025 and ended up rewriting from scratch by November. The prescription (deferred to part 2) is to keep humans reading code but front-load alignment so review is cheap.

## Core ideas / thesis

- **"i guess we doin loops now."** The prevailing wisdom ("You are the bottleneck. The models are good enough. Code is free. Just ship more stuff.") is pushing everyone to write more loops and stop reading code.
- **The lights-off factory does not work** (today). "I'm going to posit something potentially controversial: the lights off factory does not work."
- **This is not a skill issue.** "What I'm gonna try to convince you is that no amount of harness engineering or loopsmaxxing can solve what is fundamentally a model-training issue."
- **Models degrade codebase quality over time.** "They can't maintain and improve codebase quality over time -- not without a decent amount of human steering." Maintainability = Fowler's *shotgun surgery* ("really, really hard to change one part of the codebase without breaking another part").
- **Why: there's no penalty for bad design in RL.** Verifiers are one-dimensional pass/fail. "How the model got to a correct answer doesn't matter. If the tests pass, we win, but there is no penalty for eroding codebase maintainability." -> "That's how you get try catches around everything."
- **Verifying quality is orders of magnitude harder than "did the tests pass."** "Tests give you feedback in seconds, but the cost function of bad architecture is measured in weeks, months, maybe even years."
- **Model-as-judge has a ceiling.** "if a model could reliably tell good code from bad, it might have written the good version to begin with, but maintainability has no fast oracle, so we can't reward for it during RL." Review agents "raise the floor, catching the dumb stuff. But they don't move the ceiling."
- **Claude Code won because of RL inside the harness.** aider/cline/codebuff had the same tools; Anthropic "RL'd the model inside the harness -- the first time a lab trained a model against the exact tools they were going to ship it with." Corollary (citing OpenAI): "if you build a harness but you don't own the weights and can't RL the model inside it, you'll always be at a disadvantage to a team that owns both."
- **This is about brownfield/production, not vibe coding** (Addy Osmani quote). New observation: "an agent-built codebase starts to struggle after maybe three to six months."

## Architecture & mechanics

Not a tool; a diagnosis. The mental model of the factory it builds up:

**The 2022 software factory** (pre-AI loops): people decide -> tracker (Linear/Jira "state machine") -> someone builds -> PR (automated checks + human review) -> loop back if wrong -> ship -> monitoring -> user complaints -> tracker. "We haven't even hit AI yet, and there are already several loops in this picture."

**Front-loading alignment:** "building takes hours or days, and so does review. So we front-load the work -- planning, architecture proposals, sprint planning -- together, as a team." Payoff: less rework; "if you've ever read a long-but-well-done PR, you know how fast the review goes when it's close-to-perfect."

**The agentic factory:** swap "someone builds" -> "an agent builds" (orchestration, harness, sandbox, model, computer use). Building drops to minutes; review still takes hours/days -> **review is the bottleneck**. Then add agentic code review, agentic regression testing (browsers/computer use), route incidents into the factory ("wake up to a PR that maybe already fixes it"), route user feedback in. "At which point the job is two questions: how much can you stuff into the queue, and how fast can you review and test what comes out?"

**The lights-off factory** (Dan Shapiro's term; StrongDM's implementation, via Simon Willison): drop human review, reinvest in testing/self-testing, sandboxes + orchestration, automated review, monitoring, rollout, user-feedback signals. "And now the job really is just one question: how much stuff can we ask the agent to build?"

**Coding-agent RL in 60 seconds** (per Calvin French-Owen): 1) generate agent traces solving a problem, 2) score traces with a verifier, 3) update weights toward good traces; repeat millions of times. SWE-bench Multilingual worked example (`fastlane__fastlane-19304`, a 2-line nil->[] fix): model starts at base commit + bug report, never sees the golden/test patch; evaluator keeps its patch, **throws away any edits to test files** ("we've caught a model quietly commenting out the failing test or splicing in a mock"), applies the test patch, runs PASS_TO_PASS + FAIL_TO_PASS.

## Notable techniques worth stealing

- **Evaluator hygiene:** discard agent edits to test files before grading; apply held-out test patch; grade FAIL_TO_PASS and PASS_TO_PASS separately. Directly reusable in any factory's verification stage.
- **Treat "review is the bottleneck" as the design constraint.** Every factory stage exists to make the review step cheaper; don't delete the step.
- **Front-load alignment** (planning/architecture) because it's the cheapest point to change your mind.
- **Discount benchmark gains** as evidence of maintainability: "I personally don't trust any improvements on today's benchmarks as an indicator that the models are suddenly good at not slopping up your codebase."
- **Watch these evals** for maintainability signal: SWE-Marathon (~400-hour tasks, compound reward), DeepSWE (never-built OSS tasks -> no contamination), Frontier Code (multi-PR; penalizes tests that don't fail pre-patch, i.e. mutation-testing-like; judge model on diff).
- **The "3-6 month brownfield" heuristic:** plan for the moment an agent-built codebase starts to slow down and change the process then.
- Failure story to design against: "You find at least one issue gnarly enough that the agent can't solve it... Eventually you have to suck it up and go dig into the codebase you stopped reading three months ago."

## Weaknesses / open questions / risks

- Dex says explicitly "I can't prove this. You can't prove it either." Faros data is "more of a correlation signal than a verifiable smoking gun." (Part 3 partially addresses this with SlopCodeBench.)
- "RL != Benchmarks" — he infers training practices from public benchmark design; labs may have internal quality rewards.
- The StrongDM outcome is unknown ("I haven't been able to dig up any definitive data/findings").
- Conflates several independent axes (harness quality, model capability, process); the "ceiling" argument assumes judging is as hard as generating, which isn't obviously true.
- He hedges: "Maybe a future model just gets this and we can stop."

## Fit for our agentic stack

- **Adopt:** the stance that human code review stays in the loop and that the factory's job is to make review cheap (small, well-planned, vertically-sliced PRs). Design our pipeline so every autonomous stage terminates in a human-reviewable artifact.
- **Adopt:** test-file quarantine in our verification harness (agents may not modify tests in a "fix" task; or diff tests separately and require human sign-off).
- **Adapt:** we don't own weights, so per Dex we can't fix the ceiling via harness. Instead, use harness for *floor-raising* (linters, complexity backpressure, review agents) and humans + planning for the ceiling.
- **Adapt:** add a "maintainability watch" — track duplication, cyclomatic complexity, propagation cost over time in the repo (see part 3's slop-meter) as an early warning for the 3-6 month cliff.
- **Skip:** the fully lights-off mode (no human read) for anything beyond throwaway/prototype work.
