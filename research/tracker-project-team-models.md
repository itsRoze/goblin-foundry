# How trackers model Project vs. owning unit vs. Issue

**Date:** 2026-08-27
**Status:** Input for the tracker's App > Project > Ticket data-model decision
**Sources:** Primary only — linear.app/docs, Linear SDK schema (github.com/linear/linear), support.atlassian.com, docs.github.com + GitHub GraphQL schema (via `gh api graphql` introspection), shortcut.com/help + Shortcut OpenAPI spec (developer.shortcut.com)

## One-paragraph summary

All four tools agree on one thing: the **owning unit** (Linear team, Jira project, GitHub repository, Shortcut workflow) is the *required, singular* home of an issue, and it determines the issue's identifier and workflow. The **Project** (Linear project, Jira board, GitHub Project v2, Shortcut project) is an *optional, secondary* grouping. Where a project can span owning units (Linear, Jira boards, GitHub Projects), the issue's owning unit is set independently and the project's team set is either a soft constraint (Linear) or purely a view (Jira/GitHub). The exception is Shortcut, whose project is single-workflow and is now deprecated in favor of custom fields. Nobody derives an issue's owner from its project. Deleting a project never deletes issues; deleting an owning unit does.

## Linear — Team > Issue, Project is multi-team

1. **Span teams?** Yes; the project itself is multi-team, not team-less. "Projects can be shared across multiple teams. Add more teams when creating a project or from the project details page by clicking on the team name, then marking off more teams in the dropdown." [docs/projects](https://linear.app/docs/projects). Schema: `Project.teams` "Teams associated with this project."; `ProjectCreateInput.teamIds: [String!]!` (required, non-empty list) — a project cannot be team-less. [schema.graphql](https://raw.githubusercontent.com/linear/linear/master/packages/sdk/src/schema.graphql)
2. **Issue team vs project?** Set independently and required; project is optional. `Issue.team: Team!` — "Every issue must belong to exactly one team, which determines the available workflow states, labels, and other team-specific configuration." `Issue.project: Project` — "Null if the issue is not part of any project." `IssueCreateInput.teamId: String!`, `projectId: String` (optional). [schema.graphql](https://raw.githubusercontent.com/linear/linear/master/packages/sdk/src/schema.graphql). Docs: "Issues are tied to teams… issues can only be tied to one team" while "Projects can belong to a single team or be shared across many teams." [docs/teams](https://linear.app/docs/teams). The constraint is soft: an issue's team must be *among* the project's teams, enforced on move — "Projects: These are removed [when moving an issue to another team]. Add the new team to the current team's project before moving the issue." [docs/editing-issues](https://linear.app/docs/editing-issues)
3. **Lifecycle.** Deleting a project does not delete issues; the project is recoverable: "deleted projects can be found in the team's archive under the 'Recently deleted projects' tab for 30 days before they are permanently deleted." [docs/projects](https://linear.app/docs/projects). Project completion gates issue auto-archive: "Issues in active cycles or unfinished projects are archived only after those cycles or projects have also been completed." [docs/delete-archive-issues](https://linear.app/docs/delete-archive-issues). Deleting the *team* is the destructive path: "Deleting the team will also permanently delete its issues." Retiring instead makes them read-only, and "Projects only associated with retired teams become read-only." [docs/teams](https://linear.app/docs/teams). Removing a team from a project is not documented; the move behavior above implies the issue loses the project, not the team.

## Jira Cloud — Project (owning unit) > Issue; Board is a filter view

Note: Jira's "project" is the *owning unit* (key prefix, schemes, workflows), and its cross-project grouping is the **board** (company-managed, filter-backed). Atlassian now calls projects "spaces" in the docs.

1. **Span?** Company-managed boards do: "Jira allows you to create a company-managed board that displays work items from multiple spaces." The board is owned by the filter, not a project: "This new board will be available to all users who have access to your chosen filter." [create-a-board-based-on-filters](https://support.atlassian.com/jira-software-cloud/docs/create-a-board-based-on-filters/). Company-managed is "the best choice for teams who want to work with other teams across many spaces in a standard way." [team-managed vs company-managed](https://support.atlassian.com/jira-software-cloud/docs/what-are-team-managed-and-company-managed-projects/)
2. **Issue's project vs board?** Independent and derived from nothing: a work item lives in exactly one space and is on any board whose JQL matches it. The separate `Team` field is a custom field: "the Team custom field" lets you "associate issues with a specific team"; spaces are only loosely linked to teams ("Jira spaces can be linked with the teams that work in them"). [Teams in Jira projects](https://support.atlassian.com/platform-experiences/docs/using-atlassian-teams-in-jira-projects/)
3. **Lifecycle.** Moving a work item between spaces re-keys it: "When you move an work item to a different project or rename a project, the work item keys change." and "Jira reserves all previous historical keys, so… the link (pointing to its historical key)… will still work." [historical keys KB](https://support.atlassian.com/migration/kb/migration-of-jiras-historical-keys-for-issues-and-projects/). Moving also maps statuses and can drop data: "If work types use different workflows, you may lose data when bulk moving work items." [move-multiple-issues](https://support.atlassian.com/jira-software-cloud/docs/move-multiple-issues/). Trashing a space takes its issues with it: "Spaces along with their work items, components, attachments, and versions will be available in trash for 60 days, after which they will be permanently deleted." [trash](https://support.atlassian.com/jira-cloud-administration/docs/trash-for-jira-cloud-projects/). Archiving keeps them but read-only: "When a space is archived, its work items won't appear in basic or advanced search results." [archive](https://support.atlassian.com/jira-cloud-administration/docs/archive-a-project/). Deleting a board or filter never touches issues.

## GitHub Projects v2 — Repository > Issue; Project is owner-level and repo-less

1. **Span repos?** Yes; the project is repository-less (owned by an org or user). "A project is an adaptable table, board, and roadmap that integrates with your issues and pull requests… at the user or organization level." [about-projects](https://docs.github.com/en/issues/planning-and-tracking-with-projects/learning-about-projects/about-projects). "Organization projects can track issues and pull requests from the organization's repositories." / "User projects can track issues and pull requests from the repositories owned by your personal account." [creating-a-project](https://docs.github.com/en/issues/planning-and-tracking-with-projects/creating-projects/creating-a-project). Repo linking is cosmetic: "You can only list projects that are owned by the same user or organization that owns the repository." [adding-your-project-to-a-repository](https://docs.github.com/en/issues/planning-and-tracking-with-projects/managing-your-project/adding-your-project-to-a-repository)
2. **Issue's repo vs project?** Fully independent; membership is a join row. GraphQL: `Issue.repository` "The repository associated with this node."; `Issue.projectItems` "List of project items associated with this issue." (plural — one issue, many projects); `ProjectV2Item.project` "The project that contains this item." and `ProjectV2Item.content` "The content of the referenced draft issue, issue, pull request" (GitHub GraphQL schema, introspected via `gh api graphql`; reference at [docs.github.com/en/graphql/reference/objects](https://docs.github.com/en/graphql/reference/objects)). The only constraint is same-owner, enforced at the project level, not per issue.
3. **Lifecycle.** Removing an item only removes the join: "You can archive an item to keep the context about the item in the project but remove it from the project views." / "You can delete an item to remove it from the project entirely." [archiving-items](https://docs.github.com/en/issues/planning-and-tracking-with-projects/managing-items-in-your-project/archiving-items-from-your-project). Closing a project keeps everything: "You can close a project to remove it from the list of projects but retain the contents and ability to re-open the project later." Deleting is permanent for the project only: "You can delete a project to permanently remove it." [closing-and-deleting](https://docs.github.com/en/issues/planning-and-tracking-with-projects/managing-your-project/closing-and-deleting-your-projects). Transferring an issue between repos: "You can only transfer issues between repositories owned by the same user or organization account." [transferring-an-issue](https://docs.github.com/en/issues/tracking-your-work-with-issues/administering-issues/transferring-an-issue-to-another-repository) — project membership is not addressed in the transfer doc.

## Shortcut — Workflow/Team > Story; Project is single-workflow and deprecated

1. **Span?** No. A project belongs to exactly one workflow: `Project.workflow_id` "The ID of the workflow the project belongs to." and `Project.team_id` "The ID of the team the project belongs to." (both required on the object; `CreateProject` requires `team_id`). Schema description: "Projects typically map to teams (such as Frontend, Backend, Mobile, Devops, etc) but can represent any open-ended product, component, or initiative." [OpenAPI spec](https://developer.shortcut.com/api/rest/v3/shortcut.openapi.json). Docs: "Although Projects are now optional, they are still associated with Workflows." and "New Shortcut organizations will not have access to Projects as it is a legacy feature… phased out in favor of Custom Fields." [help/projects](https://www.shortcut.com/help/fields-and-features/projects)
2. **Story's team/workflow vs project?** Workflow is constrained by project (the UI filters: "selecting a Workflow will filter the available Projects to only those associated with the selected Workflow"), while Team (`group_id`) is independent and optional. `CreateStoryParams` requires only `name`; `project_id` and `group_id` are nullable ("The ID of the project the story belongs to." / "The id of the group to associate with this story."). [OpenAPI spec](https://developer.shortcut.com/api/rest/v3/shortcut.openapi.json). "When creating a Story, you no longer need to assign a Project and can now leave it blank if you choose to!" [help/projects](https://www.shortcut.com/help/fields-and-features/projects). Teams link to workflows via `Group.workflow_ids` "The Workflow IDs contained within the Group."
3. **Lifecycle.** Project deletion is blocked while stories exist: "Projects can only be deleted if all associated Stories are moved or deleted. In the case that the Project cannot be deleted, you will receive a 422 response." [OpenAPI, DELETE /api/v3/projects/{id}](https://developer.shortcut.com/api/rest/v3/shortcut.openapi.json). Archiving hides: "Archiving a Project excludes it and all its Stories from Reports, Charts, and other places within your Workspace." [help/projects](https://www.shortcut.com/help/fields-and-features/projects)

## Convergence table

| | Owning unit on issue | Project on issue | Project spans units? | Constraint | Project delete → issues |
|---|---|---|---|---|---|
| Linear | required, one team | optional | yes, explicit `teamIds` (non-empty) | issue.team ∈ project.teams; violation drops project | untouched; 30-day undelete |
| Jira | required, one space (key) | board = filter; n:m | yes (company-managed filter boards) | none (JQL) | untouched (space trash deletes) |
| GitHub | required, one repo | optional; n:m join | yes; owner-level, repo-less | same owner as project | untouched (close keeps items) |
| Shortcut | required workflow; team optional | optional (legacy) | no; one workflow | project ⇒ workflow | blocked until stories moved |

## Implications for the tracker (App > Project > Ticket, orphans allowed)

**Pattern the tools converge on:** the *owning unit* is a required scalar FK on the issue and is the source of identity and workflow; the *project* is an optional, separately-set grouping; the project's set of owning units is at most a validation rule on membership, never the source of the issue's owner. Deleting a project is a soft operation that detaches, never cascades.

**Recommendation — Ticket.app independent (nullable), Project.app single and required, membership constrained:**
- `Ticket.app_id` nullable, `Ticket.project_id` nullable, set independently. Orphans are already in scope; this makes "no app" and "no project" the same shape as Linear's `project: null` / Shortcut's nullable `project_id`.
- `Project.app_id` required and single. The tracker is solo and an App owns one git repository, so the multi-team case Linear solves (cross-team initiatives) has no analogue: a project spanning two repos is really two projects under an initiative, which is Linear's own layering ("Initiatives sit above projects… An initiative can contain multiple projects." [docs/conceptual-model](https://linear.app/docs/conceptual-model)). App-less projects are the Shortcut legacy shape and add a null branch everywhere for no user.
- Invariant, Linear-style: `ticket.project_id != null ⇒ ticket.app_id == project.app_id`. On attaching a ticket to a project, *fill* `app_id` from the project when null (convenience, not derivation), and reject when non-null and different. On moving a ticket to another app, clear `project_id` (Linear's exact behavior) rather than silently re-homing.
- Lifecycle: deleting/archiving a project sets `project_id = null` on its tickets (GitHub/Linear) or, if you want Shortcut's guardrail, refuse while open tickets remain. Deleting an app is the only cascade (Linear team delete, Jira space trash); prefer archive → read-only.

**Trade-offs.** Independent-but-constrained costs one invariant check on three mutations (attach, move ticket, move project) and a decision for "move project to another app" (Linear has no such operation; simplest is: re-home all tickets or forbid). The alternative — deriving `app_id` through `project_id` — removes one column but makes orphans second-class (a ticket with an app and no project has nowhere to store the app) and forces a JOIN for the most common filter, `tickets where app = X`. Fully independent with no constraint (GitHub) is simplest but lets a ticket claim project P of app A while sitting in app B, which is meaningless when the App is the git repo the agent will actually clone.
