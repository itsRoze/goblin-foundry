# Synthesis A — Runtime & Execution (pi + cloud sandboxes)

- **Scope:** `research/runtime/*` (5 files) + `research/sandboxes/*` (11 files). Decisions taken as given: runtime = pi (earendil-works/pi), solo dev, cloud sandboxes, open-source factory.
- **Written:** 2026-08-26. Citations are `[dir/file.md]`.

## 1. What we now know

1. **pi core is deliberately empty where a factory needs the most:** no permissions, no sandbox, no sub-agents, no MCP, no orchestration. 4 tools, <1k-token prompt, everything else is a TypeScript extension. "Pi does not include a built-in permission system for restricting filesystem, process, network, or credential access." Isolation is explicitly the VM/container's job. `[runtime/pi.md]` `[runtime/pi-remote-and-sandboxing.md]`
2. **The extension API is rich enough to build the whole worker-side of a factory without forking pi:** `tool_call` (block/mutate), `tool_result` (rewrite), `before_agent_start`/`context` (inject/prune), `before_provider_request`/`after_provider_response` (telemetry, cost caps, gateway routing), `session_before_compact`/`session_compact` (custom compaction), `pi.appendEntry` (durable state that forks correctly), `terminate:true` structured output, tool overriding by name + `operations` injection to relocate `read/write/edit/bash` into a VM/SSH box. ~35 events total. `[runtime/pi.md]`
3. **Three headless seams, in maturity order:** (a) `pi --mode rpc` / `--mode json -p` JSONL on stdio, one process per session, any language — stable; (b) SDK `createAgentSession()` in-process — stable; (c) `pi-server`/`pi-client`/`pi-protocol` (CBOR, leases, authoritative snapshots) — "Experimental … may change or be removed without notice", no shipped service or CLI, you implement `PiServerService`. `[runtime/pi-remote-and-sandboxing.md]`
4. **Two headless gotchas already documented by users:** close stdin explicitly when spawning `pi -p` (else it "sit[s] forever waiting for piped input"); RPC framing must split on `\n` only, not Node `readline`. `--session-id` is create-or-continue, so "run" and "re-prompt with a correction" are the same call. `[runtime/disler-pi-factories.md]` `[runtime/pi.md]`
5. **pi is preinstalled or first-party-templated on most serious sandbox providers:** exe.dev `exeuntu` (prebuilt binary tarball, no Node needed), Vercel `universal` image (Dockerfile line 88), E2B `pi` template + `docs.e2b.dev/agents/pi`, Daytona `@daytona/pi`, Fly `pi-sprites`, Gondolin `pi-gondolin.ts`. Everywhere else it is `npm i -g @earendil-works/pi-coding-agent` on Node ≥24 (Sprites base image ships Node 22 — nvm or Bun needed). `[sandboxes/provider-comparison.md]` `[sandboxes/exe-dev-factory-series.md]` `[sandboxes/sprites.md]`
6. **Secrets-never-in-the-VM is now table stakes and exists in five independent implementations:** exe.dev integrations (`*.int.exe.xyz`), Vercel credentials brokering (header transforms at firewall, path/method matchers), Cloudflare `outboundByHost`, Daytona `dtn_secret_*` placeholders, Gondolin placeholder secrets, E2B workload identity (beta), Sprites Connectors, Modal Caddy sidecar (alpha). Only exe.dev, Vercel, Cloudflare, Daytona and Gondolin do it for the LLM key today. `[sandboxes/provider-comparison.md]` `[sandboxes/vercel-sandbox.md]` `[sandboxes/cloudflare-sandbox.md]` `[sandboxes/daytona.md]`
7. **Fork-1:N from a warm state is the primitive that replaces git worktrees in the cloud** — and providers split cleanly on it: E2B `fork({count≤100})`, Vercel `Sandbox.fork()`, boxd live fork 100–200 ms (mem+procs), Morph Infinibranch <250 ms, Daytona VM-class only; **not** Sprites (restore-in-place only), Cloudflare (disk wiped on sleep), exe.dev (`cp` disk clone only). `[sandboxes/provider-comparison.md]` `[sandboxes/small-oss-sandboxes.md]`
8. **Cost for the reference workload (10 × 2 vCPU × 4 GiB × 4 h/day × 22 d = 880 sandbox-h/mo) spans $30–$350/mo** depending on plan floor and whether idle-while-waiting-on-LLM is billed: Sprites ~$30 realistic on $20 plan; Northflank ~$74; Morph ~$88; Cloudflare $85–198; Vercel $115–170; Daytona $150–210 (no floor, $200 credit); exe.dev $20–160 pooled; boxd ~€199; Modal $209–334; E2B ~$296 ($150 Pro floor). Nobody has measured our real duty cycle. `[sandboxes/provider-comparison.md]` and per-provider Pricing sections
9. **Firecracker providers cannot bind-mount a local checkout;** every cloud path needs a sync strategy (push branch / `git bundle` / `git diff` pull). Decide early: workers push `refs/sandbox/<run>` or `agent/<id>` branches vs orchestrator pulls patches. `[sandboxes/provider-comparison.md]` `[runtime/disler-pi-factories.md]` `[sandboxes/daytona.md]`
10. **The only public pi-in-cloud-VM factories are disler's SSSF/Inkwell (Python controller, exe.dev VMs, typed envelopes + gates + SQLite WAL trace, two-tier `sbx-` runtime keys) and Vercel's Foreman/eve template (stations, tokens injected at firewall).** Both put orchestration outside pi and treat pi as a bounded phase executor. `[runtime/disler-pi-factories.md]` `[sandboxes/vercel-sandbox.md]`
11. **pi-chat is Earendil's only fleet reference:** one Gondolin micro-VM + one pi session per channel, detached tmux workers, 15-second status snapshot files. Gondolin needs QEMU/krun on the host, i.e. nested virt or bare metal in the cloud. `[runtime/pi-remote-and-sandboxing.md]` `[sandboxes/small-oss-sandboxes.md]`
12. **Sub-agent packages are a design library, not a dependency:** 30+ overlapping packages, two incompatible RPC conventions, all in-process ones share one `~/.pi/agent` auth and one Node process. Worth copying: capability ceilings, JSON-schema delegation envelopes, launch-contract digests, `gate: "npm test"` verification, journaled `resumeFromRunId` replay, slot accounting with abandoned-slot reclaim. `[runtime/pi-extensions-catalog.md]`
13. **The maintainers are philosophically against opaque autonomous loops** ("black box within a black box"; "keep human judgment intact") and will keep core minimal; the "cloud infrastructure" tier is where Earendil plans to monetise. Design to satisfy their constraints (inspectable JSONL sessions, orchestration outside pi, objective verification) rather than wait for upstream. `[runtime/pi-design-philosophy-posts.md]` `[runtime/pi.md]`
14. **Model/harness co-evolution is a live risk:** Opus 4.8/Sonnet 5 invent tool fields on pi's stricter `edit` schema because they were RL-trained inside Claude Code's forgiving harness. Need schema-drift monitoring per model release. `[runtime/pi-design-philosophy-posts.md]`
15. **Session format is mid-migration** (v3 JSONL tree documented; "v4" durable records + SQLite/FTS backend in flight). Session JSONL is the audit artifact everywhere (survives pause/snapshot on every provider) — pin pi version and treat session-file layout as versioned data. `[runtime/pi.md]` `[sandboxes/provider-comparison.md]`
16. **Cost-of-context evidence favours pi:** Databricks (Aug 2026) — pi + Opus 4.8 xhigh highest pass rate, ~3x less context/turn, >2x cheaper per task than Claude Code/Codex; exe.dev's "Expensively Quadratic" shows cache reads dominate after ~50k tokens. Short prompts + stable prefix are money. `[runtime/pi.md]` `[sandboxes/exe-dev-factory-series.md]`

## 3. Tensions & tradeoffs

**Agent-in-VM vs tools-in-VM (agent on controller).**
- *Agent-in-VM* (topology A in [runtime/pi-remote-and-sandboxing.md]; Docker doc; SSSF/Inkwell; every provider's own pi guide): one `pi --mode rpc` per task inside the sandbox; controller in any language; session JSONL stays with the workspace; no experimental packages; N pipes to manage; the VM must hold *some* credential for the LLM unless the provider proxies it. Evidence for: it "works today", all provider docs demo it, disler ran it in production-ish. Against: reconnect/resume on VM restart is ours; every worker needs pi installed and pinned.
- *Tools-in-VM* (topology B; Gondolin, `ssh.ts`, `pi-sprites`, `@daytona/pi`): credentials, sessions, telemetry all central; guest sees `/workspace` and placeholders; VM snapshot/resume is clean. Against: N model streams through one Node process; Gondolin needs QEMU/krun on the controller host; the first-party provider extensions are interactive-first, not headless; a controller crash kills every session's in-flight state.
- Read: A now, write the worker extension so it also works under B/C (same API). The provider-side secret proxy (Vercel/Cloudflare/Daytona/exe.dev) removes A's main weakness.

**Subprocess/RPC vs SDK in-process vs pi-server.**
- RPC: stable, language-agnostic, `extension_ui_request` gives headless HITL; framing gotchas. SDK: stable, richest control (`steer`, `followUp`, `navigateTree`), but TS-only and co-located. pi-server: designed for exactly a multi-session farm (leases, snapshots, browser client) but "may be removed without notice" and ships no service. Nobody outside Earendil has shipped on pi-server yet.

**E2B vs Vercel vs exe.dev vs Sprites (the real shortlist).**
- E2B: only one with pause-with-memory + 1:N fork + official pi template + Apache-2 infra; but $150 floor, idle billed, RAM fixed per template, no static egress IPs, secrets are plain env unless workload identity (beta).
- Vercel: pi preinstalled, fork, best credential brokering, active-CPU billing; but fs-only snapshots, 24 h cap, RAM rigid, own reaper needed, managed-only.
- exe.dev: cheapest for persistent always-on bots, best ergonomics (phone, share, SSH), best blog; but no egress policy, no SDK, pooled CPU caps true parallelism, `cp` is the only clone.
- Sprites: cheapest realistic, first-party `pi-sprites` pool + RPC service, DNS egress, Connectors; but no fork/no custom image → pool-of-N reset-by-restore, 8 vCPU fixed, no region choice, idle-pause can hit a quiet LLM wait.
- provider-comparison ranks E2B > Vercel > Daytona > Cloudflare > Sprites > exe.dev; sprites.md and exe-dev.md each argue "strong fit" for the persistent-worker model. Resolution depends on whether we want per-task ephemeral (E2B/Vercel) or long-lived pool (Sprites/exe.dev) — see Q1.

**Fork vs pool vs image.** Fork-1:N (E2B/Vercel/boxd/Morph) makes "warm clone per task" trivial; Sprites/exe.dev force a named pool restored between tasks; Cloudflare forces re-hydration from R2. Daytona's container fork is documented inconsistently.

**Secrets: proxy-injected vs capped runtime key vs plain env.** Proxy injection (Vercel/CF/Daytona/exe.dev/Gondolin) = key never in VM but TLS interception + provider lock-in; Inkwell's capped `sbx-` OpenRouter key = provider-agnostic, key *is* in VM but disposable and $-capped; E2B/Modal/Sprites per-exec env = simplest, exfiltratable. Layer: proxy where available, capped key as fallback, never bake `auth.json`.

**Egress control.** Hostname allowlists are SNI/Host-only everywhere (E2B, Vercel, Modal, Cloudflare) → git over HTTPS only, QUIC/SSH need CIDR. exe.dev and boxd have none. Daytona gates custom lists behind $500. Sprites' DNS policy blocks raw IPs unless resolved via an allowed name — the most complete.

**Deterministic controller vs LLM-written workflows.** SSSF ("Agent proposes, code disposes") and Armin ("harness loop produces over-defensive code") vs code-mode orchestrators (pi-dynamic-workflows, tintinweb) where the LLM authors the DAG in a deterministic VM. For a solo dev the deterministic controller with replayable journal is the safer default; code-mode is a later escape hatch.

**Sub-agents inside a worker vs fan-out in the controller.** Zechner: sub-agents are "a black box within a black box"; ecosystem: 30+ packages because users want them. Our workers should be single-session; fan-out (best-of-N, reviewer, differential spec analysis) lives in the controller with explicit file exchange (Amp's agent-to-agent model).

**Persistent VM vs ephemeral sandbox.** exe.dev/Amp/boxd: "robots want computers", agents build *and operate*; E2B/Modal/Cloudflare: disposable, scale-to-zero. A factory wants both: ephemeral per-task workers + a small persistent tier for bots (merge queue, flaky-test fixer, deploy babysitter).

**Tool-schema fidelity.** pi keeps schemas strict; Claude Code filters unknown keys and RL trains models on that. Either mirror Claude Code shapes or add leniency in our overrides — and re-test every model release.

## 5. Cross-links

- **Control plane / process:** the controller owns queueing, retries, fan-out, gates, and the merge queue; pi owns nothing outside one task. Envelope contract (`status/summary/artifacts/notes_for_next_agent`) must be kept in sync in three places (schema, prompt example, call site) [runtime/disler-pi-factories.md]. Lease semantics (exclusive coordinator / shared observers) and "snapshots authoritative, events transient" should be the controller's session model regardless of transport. `extension_ui_request` is the HITL channel — the control plane needs an inbox to answer it. Earendil's `absurd` (Postgres durable execution, has a pi skill) is a candidate outer loop.
- **Validation / versioning:** gates run *after* execution on artifacts (`diff_matches_claims`, `tests_pass`, `writes:` diff), never on model claims; merge queue runs *all* tests pre-merge and may amend commits; `resumeFromRunId` journaled replay and launch-contract digests (agent def + model + tools hash) give reproducibility. Pin pi version per image (`ARG PI_VERSION`); session-format v3→v4 migration is a versioned-data concern; tool-schema drift needs a per-model-release eval. `pi-evals` records real sessions for skill/prompt A/B.
- **Field lessons:** exe.dev's series (merge queue > CI, review-the-reviews with numbered items, 11-line named bots, Botiquette, "ask for the design after the build", differential spec analysis) and Armin's rubrics ("make the bad state impossible", "verify independently, don't trust the ticket analysis", objective verification for outer loops) belong in the process/prompt layer, not the runtime. Inkwell's "humans decide teardown; agents recommend" is a control-plane rule.
- **Secrets & identity** cut across all themes: the runtime decision (proxy vs capped key) determines what the control plane must mint/revoke per run and what the audit log can prove.
- **Observability:** session JSONL (+ `export_html`) is the provenance artifact; SSSF's single SQLite WAL trace with `adw_id/phase_id/parent_id` spans and a PID table is the model; pi's provider hooks are the exporter seam; pi-web is the interim dashboard.
