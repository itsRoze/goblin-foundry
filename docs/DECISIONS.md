# Decisions

Append-only. One line per decision, with why. Decisions locked before the build
started live in `docs/plan/factory-blueprint.html`; this file records what the
build itself decided.

- 2026-08-19 — M0 branch is `m0/thin-slice`, conventional commits. Why: kickoff agreement.
- 2026-08-19 — Postgres 17-alpine in docker on port 6432; Zero's `zero_cvr`/`zero_change` are separate databases in the same instance. Why: one container to run, no clash with a system Postgres on 5432.
- 2026-08-19 — zero-cache runs from the workspace (`just zero`), not docker-compose. Why: it needs the compiled Zero schema from `packages/schema`; mounting build output into a container buys nothing on a single dev box.
- 2026-08-19 — Postgres is snake_case; the Zero schema maps every table/column with `.from()`. Why: the worker writes raw SQL constantly, and Zero's mapping is free.
- 2026-08-19 — `event` and `transcript_entry` are excluded from Zero (publication `goblin_zero` names the synced tables explicitly). Why: the firehose goes worker → Postgres → NOTIFY → SSE; syncing it would push thousands of rows per run through logical replication and IVM.
- 2026-08-19 — Tickets point at a `status` row (`status_id`), and agents trigger on `status.kind`. Why: one source of truth for the ticket's state; kinds stay canonical while names stay per-project.
- 2026-08-19 — Timestamps are `timestamptz` in Postgres and `number()` (epoch ms) in Zero. Why: Zero maps them natively, so SQL keeps real time types.
- 2026-08-19 — Reads go through Zero (client ZQL); writes that mean something (status moves, design create/approve) go through REST on the API. Why: no custom-mutator/push plumbing in M0, and every writer — browser, planner skill, worker — uses one audited path.
- 2026-08-19 — The SSE stream accepts `?token=` as well as a bearer header. Why: browser `EventSource` cannot set headers.
- 2026-08-19 — UI reads go through named synced queries in `packages/schema/src/queries.ts`, served by the API at `/zero/query`. Why: client ZQL is legacy in Zero 1.9 and syncs nothing; this is the path Zero is keeping.
- 2026-08-19 — The web app is a hash-routed Vite app with no router dependency, styled from the blueprint's own palette. Why: three views, and the factory should look like its plan.
- 2026-08-19 — The builder runs with `permissionMode: 'bypassPermissions'` and `settingSources: []`, with a PreToolUse hook as the actual boundary. Why: hook denies apply even under bypass, so one guard covers every call — path escapes, git redirection, and policy protected paths — instead of relying on permission-rule syntax.
- 2026-08-19 — Worktrees are cut with `git worktree add -B` after a forced remove and prune. Why: `-p` runs never clean up, so a killed worker leaves a worktree and branch that would otherwise be silently reused by the next attempt.
- 2026-08-19 — The builder's prompt embeds the envelope's JSON Schema generated from the zod type. Why: disler's "synced triad" (type, prompt example, call site) drifts; generating the example removes the failure mode.
- 2026-08-19 — The planner is a skill (`/plan`) linked into `.claude/skills` by `just install-skills`, not a worker phase. Why: M0 scope — it runs in the user's terminal and writes back through the API.
- 2026-08-20 — The builder subprocess gets an explicit `env` with the factory's secrets removed, and `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=1` so the agent's own shell commands cannot read the Anthropic credential either. Why: the subprocess must hold its own credential to authenticate, so the boundary has to be one level down, at the commands the agent runs.
- 2026-08-20 — Stalled runs are swept at the top of every worker tick, not by a separate process. Why: the worker is the only thing that must be running for this to matter, and a reaper nobody starts is a reaper that does not exist.
- 2026-08-20 — A stalled ticket is requeued up to 3 failures, then left in `building` for a human. Why: the blueprint's "3 retries, then escalate" — a laptop that sleeps mid-run should recover itself; a ticket that keeps dying should stop trying.
- 2026-08-20 — M1's hand-built work lands on branch `m1` (the worktree's own branch), not `m1/<slug>`. Why: git cannot hold `m1` and `m1/questions` at once, and the M1 worktree is already checked out on `m1`; factory-built work keeps its own `goblin/fac-*` branches.
- 2026-08-20 — The planner's questions, the design gate, and the planner phase itself are hand-built, not run through the factory. Why: the kickoff's chicken-and-egg exception — they are the machinery a planner run depends on.
- 2026-08-20 — A run asks you something through `AskUserQuestion`, intercepted in `canUseTool`, and waits there. Why: it is the model's own tool, so the agent needs no special prompt vocabulary, and the callback may stay pending indefinitely, which is exactly "the run waits for you".
- 2026-08-20 — The worker waits for an answer by polling the `question` row every 2s, not by LISTEN. Why: the answer arrives through the API from a browser or a phone; one cheap query beats a second NOTIFY channel that has to survive a dropped connection.
- 2026-08-20 — The planner writes two documents: `design_markdown` for the builder and `review_html` for you, gated by `review_readable` (no scripts, no external resources) because it renders in a sandboxed iframe. Why: the blueprint's two-outputs rule, and a document a human reads is not the same artifact as a specification a builder implements.
- 2026-08-20 — Annotations accumulate on the design and are handed to the next planner run as answers, not questions. Why: you already said it once; a planner that asks it again has wasted the round.
- 2026-08-20 — The review fix loop lives inside the reviewer phase, opening a `builder_fix_N` phase per loop, rather than as a loop in the sequencer. Why: the sequencer stays a straight line of phases, and the loop is the reviewer's own bounded correction — the same shape as a failed gate.
- 2026-08-20 — A reviewer run attaches a worktree to the existing branch and diffs against its merge-base with the default branch. Why: the build that produced the branch removed its worktree, and the change under review is the branch's own work, not everything main has done since.
- 2026-08-20 — A ticket whose last run for the same trigger failed is not re-claimed until the ticket is touched. Why: the review pipeline leaves the ticket in In Review, so without this a failed review would loop forever; moving the card is how you say "try again".
- 2026-08-20 — Budget exhaustion and usage limits are named terminal reasons that end a phase immediately, never retried. Why: a retry buys the same failure at the same price, and "worker_error" hides the one failure a human can actually fix.
- 2026-08-20 — The per-ticket budget is checked between phases against the run's accumulated cost. Why: `maxBudgetUsd` is per `query()`, so a phase that retries three times can spend three times its cap without anything noticing.
- 2026-08-20 — Every answer you have given on a ticket goes into the next planner run's opening prompt as settled. Why: a run that dies mid-interview must not cost you the interview.
- 2026-08-20 — TEMPORARY: the factory project's `default_branch` is `m1` while M1 is being built, and goes back to `main` when M1 merges. Why: the factory was cutting every worktree from `main`, so the planner designed and the builder built against a codebase missing every M1 feature — the base branch is per-project data precisely so it can follow the work, and leaving it on trunk during milestone work is the bug, not the column.
- 2026-08-20 — Every project gets a unique, uppercase `key`, derived from its slug (initials of a multi-word slug, first three letters of a single-word one, `P`-prefixed if that would start with a digit, numeric suffix on collision) and overridable; `goblin-foundry` is overridden to `FAC`. Why: FAC-10 — a ticket number is only unique within a project, and a ref that lists work across every project needs a project-qualifying prefix.
- 2026-08-20 — Canonical ticket URLs are `#/<KEY>-<n>` (e.g. `#/FAC-10`), superseding `#/t/<n>`. The legacy form still resolves — rewriting itself to canonical when the number is unambiguous, and showing a chooser rather than guessing when more than one project has it. Why: FAC-10 — a ref has to mean the same ticket in a URL as everywhere else, and an old link must not silently open the wrong project's ticket once a second project exists.
- 2026-08-20 — Worker branch names are cut from the ticket's project key (`goblin/<key>-<n>`), not the hard-coded `goblin/fac-*` recorded above (2026-08-20, M1 branch note). Why: FAC-10 — the same reasoning as the URL change; a second project's branches need their own prefix.
- 2026-08-20 — The API's ticket lookup returns `409` for a bare ticket number more than one project has, rather than picking a row. Why: FAC-10 — the old behaviour returned whichever row Postgres offered first, silently opening the wrong ticket; an explicit ambiguity error is the honest response once two projects can share a number.
- 2026-08-21 — The `TriggerStage` table (working/delegate/success per trigger status kind) moved into `@goblin/schema` as `TRIGGER_STAGES`; `apps/worker/src/pipelines.ts` spreads it into each `Pipeline` instead of restating the triple. Why: FAC-10 — the inbox's stuck predicate needs the same mapping the worker uses to claim tickets, and a second copy in the web app would rot the moment one drifted from the other.
- 2026-08-21 — The inbox's rounds, approvals and stuck candidates are three separate named synced queries (`openQuestions`, `pendingApprovals`, `stuckCandidates`), read through one shared hook (`useInbox.ts`) that both the topbar badge and the inbox page call, rather than each computing its own. Why: FAC-10 — "the badge and the page are derived from the same function" is only actually guaranteed if they call the same code, not merely equivalent code.
- 2026-08-21 — The inbox's full-screen breakpoint is 720px, done as a CSS media query on `.inbox-expanded` rather than a JS `matchMedia` branch. Why: FAC-10 — the expand/collapse state (which item, if any) lives in the URL either way; only the *presentation* changes at narrow widths, and CSS already expresses that without adding a second source of truth for viewport size.
- 2026-08-21 — Slice 2 of FAC-10 (the inbox, read-only) ships without action buttons on any expanded item — no send-round, approve/send-back, or retry/backlog — even though the shared `Design` component already has working Approve/Send-back wired to the API. Why: FAC-10's own sequencing puts "the actions" in slice 3, and the design calls out that the existing round-answer endpoint sends one answer at a time, which slice 3 is meant to replace with a single-transaction round endpoint; wiring the old flow into the inbox now would ship something slice 3 has to tear back out.
- 2026-08-20 — Turn caps are loose (planner 200, builder 300, reviewer 200) and the dollar budget is the real leash. Why: measured — the planner spent 37 turns on one design and the builder hit 80 doing correct work, so a cap tight enough to bind stops long-but-healthy runs, while a runaway loop is caught by `maxBudgetUsd` and the per-ticket cap either way.
- 2026-08-20 — Every agent gets `WebSearch` and `WebFetch`. Why: the boundary is where an agent may *write* — its worktree — not what it may know. An agent that cannot read the docs for the framework it is using guesses instead, and guesses cost more than requests; Subway Reader against Gradle and Compose would have paid this every run.
- 2026-08-20 — The guard treats a `/…` token as a path only when its first segment is a real filesystem root. Why: two thirds of every denial it ever recorded were regex flags (`/g`, `/gu,`), comments (`/**`), and quoted relative paths (`/src/slug.js`) — a false denial does not read as a harness rule from inside the agent, it reads as its own failure, and one reviewer gave up and wrote its findings as prose because of it.
- 2026-08-20 — OPEN QUESTION (FAC-19): requeuing by dragging a card back into a trigger status is a crutch, not the design. Why: status is both the ticket's state and the command that starts work, so "build the next slice", "retry", and "re-review" have no vocabulary except moving a card backwards — which lies about state, as it did when a ticket sat in Ready for Dev while a reviewer run owned it. The likely answer is that a queued run row becomes the unit of work and the worker claims runs rather than statuses; the blueprint says statuses are the triggers, so this needs a design before it changes.
- 2026-08-21 — The pi harness adapter (FAC-16) is pulled from M2 into M1, and pi phases default to OpenCode Go ($10/mo, a $12-per-5-hour-window budget behind an ordinary API key; pi ships the `opencode` provider natively). Why: Max-plan 5-hour limits keep halting development mid-milestone, and Go moves the bulk token burn to a cheap lane with no OAuth ToS risk — the harness A/B's counters, not a guess, decide what stays on Claude. The deep half (guard as a pi TS extension, JSONL session mirror, Codex-as-refuter) stays in M2.
- 2026-08-21 — A phase names its runner in policy: `harness: claude-code | pi`, with `model` read as a Claude alias (`opus`) or as `provider/model` (`opencode-go/kimi-k3`) accordingly. Why: one field decides the lane, so a tier cannot claim a provider its runner cannot reach, and the A/B is a `group by harness` over counters we already record per phase.
- 2026-08-21 — The pi runner keeps the same PreToolUse boundary by wrapping pi's tool events with `checkTool`, not yet as a pi extension (M2). Why: the thin slice should not ship a second, weaker boundary — a denied call is recorded as `permission_breach` exactly as it is under Claude Code.
- 2026-08-21 — `librarian` is the first tier on the cheap lane (`pi` + `opencode-go/kimi-k3`). Why: it is the A/B's control group — the cheapest real phase kind, where being wrong costs a wiki line rather than a branch.
- 2026-08-21 — A resumed branch merges its base before any phase runs, and a merge conflict fails the run with `base_conflict` instead of being papered over. Why: a branch reviewed and merged against a repository that has moved surfaces its conflict on the pull request, where no agent is watching and the human resolves by hand.
- 2026-08-21 — A push the remote refuses fails the phase (`push_rejected`), rather than being reported in the summary. Why: a run whose work never left the machine is not a run that succeeded, and the board said otherwise for an hour.
- 2026-08-21 — The worktree guard runs as a pi extension on the blocking `tool_call` hook, pulled forward from M2. Why: a builder that writes files needs an enforced boundary, not a log line — pi's hook can block, so one `checkTool` now covers both harnesses and a denial reads the same in either trace.
- 2026-08-21 — The builder tier moves to `pi` + `opencode-go/kimi-k2.7-code`; planner and reviewer stay on Claude Code. Why: builders are two thirds of all phases and $39 of $71 spent, so moving them is where a $10 window buys the most relief — and a code-tuned model is the fairest first test of whether the cheap lane can write code the gates accept.
- 2026-08-21 — FAC-13 adds `ticket_dep` and `project_design`. `ticket_dep` is synced to Zero and has a composite key (`blocker_id`, `blocked_id`) with cascade deletes, a self-edge check, and an index on `blocked_id`; `project_design` is server-side only. Why: dependencies are visible on the board and must follow ticket deletes; project designs are context for prompts and do not need to live in the browser.
- 2026-08-21 — A ticket is "ready" when none of its blockers are in a non-terminal kind (`done`/`canceled`). The board's blocked marker and the worker's `claim()` query share one predicate in `@goblin/schema/src/readiness.ts`. Why: the board is the only explanation the owner gets for a ticket the worker declines; drift is a bug.
- 2026-08-21 — The board groups columns by status kind, not by status row. Why: with two projects the board would otherwise double to 22 columns; grouping by kind keeps it legible while per-project names/colours still come from an enabled row of that kind.
- 2026-08-21 — The smriti importer is a one-shot script driven by `just import-smriti`, using Node's built-in `node:sqlite` read-only and a single Postgres transaction that is rolled back for `--dry-run`. Why: the predecessor is being retired, so no sync/upsert path is needed, and a dry run that exercises real constraints is more useful than a simulation.
- 2026-08-22 — Three independent limits stop a runaway: three failed attempts per ticket per trigger since you last touched the card, a sixty-second cooldown after any failure, and a global breaker that stops the worker when more than twelve runs start in ten minutes. Why: the specific guard stops the loop you thought of, and the rate breaker stops the one you did not — real work is slow, so a high run rate is never a good sign whatever its cause.
