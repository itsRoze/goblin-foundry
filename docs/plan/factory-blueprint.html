The pitch

What it feels like to use, before what it's made of.

You already have Claude Code, Linear — and smriti, your skill stack whose /begin flow and local board are a proto-factory: apps → projects → tickets in factory.db, run traces, three human gates, and a philosophy this plan adopts wholesale ("the paper trail is stored, not linked… nothing is ever committed into your repo"). What smriti can't do is what this factory adds: multiple agents on multiple tickets in parallel, a real status machine, per-project policy, full observability, and work that continues when your laptop is closed. The board decides what happens next; agents do bounded work under a per-app policy; everything they did is recorded so you can read it back. smriti's projects, tickets, and dependency edges import on day one — Subway Reader's 17 tickets come along.

Principles

The rules that decide the arguments later. Each one traces to something the research found other people learning the hard way.

  1. The board is the orchestrator. Status transitions are the API between you and the agents. Humans and agents both move cards; the project's policy says which transitions need a human.
  2. A ticket is not a run. Ticket → Run → Phase → Event. Attempts, retries, cost, and evidence live on the run. Every system that survived converged here; Vibe Kanban's migration history shows the fix.
  3. Code owns sequencing; agents own one bounded phase. Deterministic worker code decides what runs next, retries, and acceptance. Each phase returns a typed envelope; gates verify its claims mechanically and record evidence, not just pass/fail. ("Agent proposes, code disposes" — disler.)
  4. Qualify early, review with evidence. One human decision up front (approve the design), an unattended run, then a review queue where each PR arrives with gate evidence, screenshots, and a handoff note — not just a diff. Review, not compute, is the ceiling; make review cheap.
  5. Comprehension is a feature. Designs are written for you (HTML, mockups, notes) as well as agents (markdown, EARS criteria). The librarian keeps a small, loadable wiki. Every commit links back to the conversation that produced it.
  6. Correction, not restart. A failed gate re-prompts the same session with the named violation. Retry budgets are policy ("3, then escalate"), never emergent.
  7. Per-project policy, not global config. Gates, review lenses, model tiers, budgets, deploy commands vary per app.
  8. Boring primitives you control. Git, Postgres, a CLI subprocess, markdown files. The category churns violently (Vibe Kanban, Crystal, Terragon, Height, Sweep all dead or pivoted in 12 months); the layers underneath don't.
  9. Cost and stalls are first-class. Every phase has a budget; every run has a heartbeat and a pid; spend and context occupancy are tracked as different numbers.
  10. Own the event schema. OTel and Langfuse are transport or side-exports, never the source of truth for the factory floor. The OTel GenAI conventions are still unstable.

Conductor — the long-running session that runs the project

The worker's orchestrator is deterministic code that sequences phases inside a run. The Conductor is a different kind of thing: a conversational agent, one per project, that sequences tickets and owns the Project Design. In the factory metaphor it's the Foreman.

  • Roadmap → tickets. Breaks a milestone into a DAG of tracer-bullet tickets (to-tickets), sizes them, sets blocks/blocked-by, and picks what can run in parallel given max_concurrent_runs and file-overlap risk. Ready work is a projection over the graph (Beads' pattern), not a heuristic.
  • Standup on demand. "What's blocked, what's ready, what should run tonight, what did last night cost."
  • Design propagation. When a shipped ticket changes the app's shape, it updates the Project Design (new version), adjusts or opens affected tickets, and flags conflicts with in-flight designs. Ticket designs are deltas against the project design; the reviewer's spec↔code lens checks both.
  • Triage. Intake bugs and scout proposals land with it first.
  • Where you talk to it: web UI, terminal, or phone (through the MCP server) — same session, resumed by id.
Guardrail
The Conductor proposes ticket and design changes. Policy says whether it may apply them unattended (vibe: yes; serious: you approve). It never runs a build itself — it moves cards, and the board does the rest.

Planner — the grill-me interview, three perspectives, two documents

This is one of the two genuinely novel pieces (the research found essentially no prior art for an adversarial, multi-perspective planning interview). Structure, borrowed from AI Hero's grilling primitive and BMAD's persona "party mode":

  1. Triage. Full design if 2+ of: approach uncertain, touches modules that don't obviously compose, expensive to reverse, acceptance criteria not obvious from the title. Otherwise a mini design, or straight to build.
  2. Fact-finding. A subagent reads the wiki, ADRs, and similar features first — "finding facts is your job, never the user's."
  3. Grill rounds. Map the request as a decision tree; ask the whole frontier (questions whose prerequisites are settled) in one numbered round, each with a recommended answer; recompute; repeat until the frontier is empty and you confirm shared understanding.
  4. Three-perspective pass. Product / Engineering / UX subagents each critique the draft. They're allowed to disagree; unresolved disagreements become open questions thrown back to you, not silently resolved.
  5. Two outputs. design.md for the builder (goals, non-goals, EARS acceptance criteria, test plan, "notes for builder" by name and shape, never file paths). review.html for you: overview, what changes for the user, mockups (HTML wireframes first; Figma via MCP later), high-level changes by module, risks and open questions, decision log. Your annotations become the next grill round → design v2.
Human gate
The design approval is the qualification gate. Everything downstream is designed to run unattended from here, so the design has to carry the intent: scope boundaries, criteria, and what the builder may decide alone.

Reviewer — lenses, isolation, refutation

The second novel piece: nobody structures multi-lens review as separate, isolated, scored passes. Each lens is its own subagent that sees only the diff, the design, and its brief — never other lenses' findings or the builder's reasoning. Findings are reported side by side, never merged into one ranking ("reporting them separately stops one axis from masking the other"). A refuter subagent then tries to disprove each finding; what doesn't survive is dropped or downgraded.

  • Lenses: correctness/spec-fidelity (criteria ↔ diff, line by line), security (trace input to sink or say you can't), performance (name the trigger condition or it isn't a finding), tests (every criterion has a test; flag tautological and implementation-coupled tests), maintainability/standards (repo standards first, then a fixed smell baseline), UX (only for user-facing changes). Projects pick their subset in policy.
  • Severity: important / nit / pre-existing. Only important blocks by default.
  • Fix loop: blocking findings resume the builder's session (correction, not restart). Policy sets the cap — default 3 — then the ticket goes to Needs you with the findings attached.
  • Claude Code's /code-review can be a lens implementation (it runs headlessly); ultrareview needs claude.ai auth.

Builder — definition of done, enforced by hooks

  • Own worktree and branch; nothing outside declared scope; protected paths enforced by post-hoc diff (the harness rolls back a breach and re-prompts).
  • Red before green per slice; every acceptance criterion has a test; full typecheck + test + build + lint at the end.
  • Verify lane. Run the app and walk the acceptance criteria before self-review, attaching evidence (Cursor's "demo artifacts" pattern): web via Playwright / Chrome DevTools MCP with screenshots; Android via the emulator (gradle managed devices or adb install/launch/screencap, Maestro for UI flows, e-ink sanity = high-contrast screenshots at Boox resolution) — this is Subway Reader's path; iOS later via xcrun simctl + xcodebuild test (an iOS worker must be a Mac).
  • Ephemeral data. Every run gets its own database — a Postgres DB cloned from a fixtures template per worktree (or a Supabase branch), connection string injected into the worktree's .env by the worker, torn down with the worktree. Prod credentials never reach a builder; the policy's access block says who gets what.
  • Self-review in a fresh subagent that sees only the diff and design; then a 1–2k-token handoff note: what, evidence (commands + output, screenshots), deviations, decisions made alone, open questions.
  • Ambiguity rule: decide-and-log when reversible and one-sentence-describable; stop and ask when it changes the approach, expands scope, or after two failed self-corrections.
  • Enforced by a Stop hook / gates, not by asking nicely — with a circuit breaker so a mis-specified check can't loop forever.

Librarian — a wiki small enough to load

Four artifacts, one routing table, one index. Commands and conventions → CLAUDE.md; "why" behind hard-to-reverse decisions → docs/adr/; domain terms → CONTEXT.md; repeated mistakes → lessons.md; user-visible changes → CHANGELOG.md. One index file every agent loads (cap ~200 lines / 25 KB, the same budget Claude Code uses for its own memory); everything else read on demand. No vector search until the wiki outgrows ~200k tokens. Most tickets produce a changelog line and nothing else — that's fine.

Where the wiki lives

Your rule: code is the documentation; doc files exist only for context code can't explain; nothing else pollutes the garden. So the repo keeps exactly two kinds of files: CLAUDE.md/AGENTS.md (commands, conventions — the things tooling already reads) and, optionally, ADRs when a decision is genuinely inexplicable from code. Everything else — glossary, lessons.md, changelog drafts, design docs, the index — lives in the factory DB, exactly like smriti's document store. The worker materializes the relevant slice into each worktree at run start (git-ignored path) so agents still read it with cheap file tools; the DB is authoritative once the worktree is gone. The librarian writes to the DB and touches the repo only for CLAUDE.md updates. Cross-project knowledge is a factory-level wiki in the same store, loaded by every planner and the Conductor.

Deployer and Scout

Deployer exists because you defined Done as "live in prod." Mostly code: merge, run policy.commands.deploy, run policy.commands.verify, attach evidence. For iOS, "Done" needs its own definition (submitted to TestFlight / App Review with a verified build) since Apple's review isn't yours to automate. Scout is your "agent that proposes ticket ideas": periodic, read-only, feeds on lessons.md, review-finding history, and cost metrics, and files proposals you accept or reject in the Backlog.

Why these choices

  • Agent SDK in a worker, not a spawned CLI. The SDK is the CLI (one query() = one claude subprocess) but gives you typed messages, in-process hooks, canUseTool for approvals and AskUserQuestion, sessionStore to mirror transcripts into Postgres, and interrupt(). Skip Managed Agents (no worktrees, hooks, or prompt capture) and Agent Teams (don't run headlessly).
  • One query() per phase. Clean per-phase cost, model, effort, tool allowlist, maxTurns, maxBudgetUsd, and a JSON-schema outputFormat for the envelope. Resume the same session for corrections; fork for speculative retries.
  • Zero from zbugs. Rocicorp's demo is a Linear clone: schema, filtered list query, j/k navigation, reactions, and the mutator pattern transfer directly. Zero is 1.9 (1.0 shipped June 2026), self-host only, no offline writes — acceptable for a personal tool on one box.
  • Postgres does triple duty: Zero's upstream, the event log, and the job queue (SELECT … FOR UPDATE SKIP LOCKED + leases). No Redis until it hurts.
  • Worktrees, not containers, for local isolation — the field converged there. Containers only when work leaves your machine.
  • Auth: your Max subscription first. claude setup-token mints a one-year OAuth token that headless sessions accept for model requests. Anthropic's restriction targets third parties offering claude.ai login in their products; personal automation on your own seat isn't addressed either way. Plan windows (5-hour + weekly) can drain overnight, so the worker reads plan usage and fails over to an API key per phase — auth is just env on each query(). Subscription sessions also get the 1-hour prompt-cache TTL for free.
  • Harness-neutral spine, Claude-first adapter. Phases record coding_agent; events use a normalized schema (Vibe Kanban's NormalizedEntry idea). Build the Claude adapter without the abstraction; write the second (Codex CLI is the obvious one — you have it) when it's real. Model routing (Bedrock/Vertex/gateway) keeps the harness; a chat router like OpenRouter is for cheap non-agentic calls (planning critic, dedupe, classification) behind one llm() helper, and later a non-Claude refuter in review.

Prompt lineage — the third novel piece

Nobody answers "this exact prompt was assembled from CLAUDE.md v7 + these skills + this design v3 + this ticket body." Record it per phase as prompts.lineage: shas of the wiki index, CLAUDE.md, each SKILL.md, the design version, the ticket body, the system-prompt append, plus model/effort. Then a prompt change is an experiment you can compare on the counters above, and a bad run can be replayed.

Hybrid
Own the event log and the UI. Optionally dual-export OTel to a self-hosted Langfuse or Phoenix for deep trace debugging and eval datasets — later, and only if the built-in trace view isn't enough.

Provenance — snapshotting what produced the code

Your "new Git" instinct, made practical: git keeps versioning code; the factory versions everything upstream of the code and links the two both ways.

The minimal scheme that gets you "click any line, see the conversation, design, and review that produced it":

  1. Trailers on every agent commit: Factory-Ticket: FAC-12, Factory-Run: run_…, Factory-Phase: builder/2, Factory-Design: v3, plus Co-Authored-By. Grep-able forever, survives rebases better than notes.
  2. A provenance block in every PR body: links to the run trace, design version, review findings, handoff note, and cost. Cursor and Copilot both found this is the single biggest review-cost win.
  3. Designs are stored, not committed (your call, and smriti's rule): design versions live in the factory DB; the worker materializes the active design into the worktree at run start (git-ignored path) so agents read it with file tools, and the DB wins when the worktree is gone. The reviewer's spec↔code drift lens reads the design via the factory, not the repo. Commit trailers carry the design version, so the snapshot link survives without polluting the garden.
  4. The database keeps the rest: full transcripts (sessionStore), compiled prompts + lineage, questions and answers, review findings, design versions with your annotations — all keyed by run/phase.
  5. Reverse index: git blame → sha → trailer → run → the whole trail. Optionally mirror a run-summary JSON into git notes so it travels with the repo.

Where Delta and Cursor Origin fit

Zed Delta is the closest thing to what you described: DeltaDB captures "the conversation and the worktree together, in real time" — every edit and conversation turn between commits, with comments anchorable to code or chat. But it's explicitly a companion to git ("works with the git repository you already have"), it's in private beta as of this month, and there's no public API, license, or pricing yet — its only integration is Delta calling into Claude Code, not tools writing into DeltaDB. Cursor Origin turns out to be Cursor's new git-hosting platform (announced two days ago, on a storage engine called Continuity): push-level provenance for repos, not conversation capture.

So: build the scheme above now on Postgres + trailers — it's what Amp does today with its Amp-Thread trailer, and what Copilot does by linking commits to session logs — and treat Delta as a possible transcript store behind step 4 once it has an API. Nothing in the linking scheme has to change; only where transcripts live. Worth an experiment in M4, not a dependency.

Phone & overnight

Continuity is the requirement: see status and approve from bed; builds keep going after you close the lid.

Phone

  • Responsive web first — the board, approvals inbox, and ticket page must work on a phone from M0; the trace view can be desktop-only for a while.
  • Factory MCP server (M2) — list_tickets, get_run, approve_design, answer_question, create_ticket, kick_off, plan_ticket. Connect it to the Claude app and your phone becomes a conversational console: "what's blocking FAC-12?", "approve it", or a full grill-me session on the couch with results written back to the ticket. Needs a reachable HTTPS endpoint (Tailscale Funnel or Cloudflare Tunnel from the Mac; trivial once on a box).
  • Claude Code Remote Control for driving a live desktop session from the phone — covers "continue development on the fly" for interactive planning before the MCP path exists.
  • Push notifications for Needs-you events (ntfy or similar), deep-linking to the approvals inbox.

Overnight

  • M0–M2: worker on the Mac; caffeinate while runs are active; the scheduler pauses new claims when the machine will sleep.
  • M3: move api + worker + Postgres + zero-cache to an always-on box (Mac mini at home is ideal — iOS builds need macOS anyway; or Fly.io / exe.dev-style host for web-only projects). The interfaces are the same; only cwd and secrets move.
  • Budgets are what make overnight safe: per-phase maxBudgetUsd, per-ticket cap, stall timeout with heartbeat, and a hard cap on concurrent runs. Failure escalates to Needs you with evidence, never retries forever.

Roadmap

Five milestones, each ending in something you'd actually use. Weekend estimates assume nights-and-weekends pace and heavy use of Claude Code to build the factory itself.

M0Thin vertical sliceweekends 1–2

One ticket goes Backlog → Ready for Design → (planner in your terminal) → Design Review → approve on the web → Ready for Dev → builder in a worktree → PR, while you watch a live run trace.

  • Scaffold the monorepo; docker-compose Postgres (wal_level=logical) + zero-cache; Zero schema from a zbugs subset (project, ticket, comment, label) plus run/phase/event tables.
  • Web: board (statuses as columns), ticket page (body, design tab, runs tab), run trace (lanes + event feed over SSE), approve button. Keep it usable on a phone.
